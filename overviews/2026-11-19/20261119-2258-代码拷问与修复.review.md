## 应该改（Should）

### [Should] packages/foundation/bridge-slices/compiler/ts/src/plugins/runtime-adapters.test.ts:293

**现象**：新增的 `failureExecution fails fast for web...` 测试直接调用 `failureExecution('web', action, ...)` 并断言 `success=false` / 无伪造事件。但 `failureExecution`（spawn.ts:23-46）本轮**未改动**，它原本就返回 `success=false`。本次真正的改动是 compiler.ts:79/82/115/118 与 compiler-worker.ts:117-123 把 `fallbackDevResult`/`buildResult('fallback')` 换成 `failureExecution`。

**为什么重要**：该测试在两处 flips 被回滚、重新变回 `fallbackDevResult` 的情况下仍会通过——它没有覆盖任何改动行，属于假绿。用户要求「测试是否真的锁定行为」，这一条没锁住。

**改法**：补一个打到改动接线的测试。例如用依赖注入/mock 让 worker 调用失败，再断言插件层返回失败：

```ts
// 思路：mock runCompilerInWorker 使其 reject，再走插件 handle
test('compiler.build fails fast on web when worker is unavailable', async () => {
  // 用现有的 module mock 机制（若项目用 t.mock / esmock）替换 runCompilerInWorker：
  //   runCompilerInWorker: async () => { throw new Error('worker down'); }
  const handled = await compilerPlugin.handle('compiler.build', { cwd: someWebProject });
  assert.equal((handled as any)?.result?.success, false);
  const methods = (handled?.events ?? []).map((e) => e.method);
  assert.ok(!methods.includes('event.compiler_server_ready'));
  assert.ok(!methods.includes('event.build_asset'));
});
```

若注入成本高，至少把 worker 的 `createFallbackExecution` 导出并单测，断言它返回 `success=false` 且不含 `event.build_asset` / `event.dev_url`。

### [Should] compiler-adapters/vite.ts:184、compiler-adapters/rollup.ts:181、compiler-adapters/webpack.ts:190（本轮 8 文件之外的既有代码）

**现象**：A3 翻转只覆盖了「worker 不可用 / adapter 返回空」两处兜底。web adapter **自身**在工具执行失败时仍返回伪造成功：

- `vite.ts:184` → `fallbackDevResult(...)`：含 `compilerDoneEvent(success=true)` + fake `http://host:port` + `event.dev_url`。
- `vite.ts:273` / `rollup.ts` / `webpack.ts:190` → `buildResult(..., 'fallback', ...)`：含 `compilerDoneEvent(success=true)` + fake `dist/index.js` + `event.build_asset`。

这些结果的 `result` 无 `success` 字段，经 Rust `resolve_dev/build_exit_code` 的 `unwrap_or(true)`（workspace dev.rs:33 / build.rs:32）被判为**成功**。

**为什么重要**：本轮意图是「全量修复 + 失败不再伪造成功」。若 vite/webpack/rollup 真实构建抛错，用户仍会看到「构建成功」并拿到假的 `dist/index.js`——与 README 契约及本次目标冲突。这是功能断点（L3），虽属 8 文件之外的既有代码，但直接决定验收目标是否达成。

**改法**：把这些 catch 分支改为失败语义，复用已 `failureExecution`：

```ts
// vite.ts handleDev catch
} catch (error) {
  return failureExecution('vite', 'dev', `vite dev failed: ${normalizeError(error).message}`);
}
// vite.ts handleBuild catch
} catch (error) {
  return failureExecution('vite', 'build', `vite build failed: ${normalizeError(error).message}`);
}
// rollup / webpack 同理（webpack dev catch 当前用 buildResult + createCompilerResult 覆盖，需整体替换）
```

并补一条 web adapter 工具失败的插件级测试，断言 `result.success === false` 且无 `event.build_asset` / `event.dev_url` / `event.compiler_server_ready`。

### [Should] packages/products/runex/rust/runex-core/src/store.rs:191/196/211

**现象**：`from_cache` 语义由「恒为 false」修为正确，但未新增任何回归测试。全仓 grep 无 `from_cache` 相关测试（commands.rs:249 仅为输出字段透传）。

**为什么重要**：该 bug 是「语义写反」——代码看起来像对的、实际恒错，且 design doc §17.2 #1 记录后长期未修。这类静默语义反转最容易再次回归，没有测试锁定就只剩人工 review 兜底。

**改法**：在 runex-core 增加针对 `InstallOutcome.from_cache` 的测试，覆盖两态：

- 预置某个 artifact 到 `downloads_dir()` 的缓存路径（有效校验和）→ 安装后断言 `outcome.from_cache == true`。
- 预置一个坏文件（校验和不匹配）触发重下，或不预置 → 断言 `outcome.from_cache == false`。

可复用现有 mock provider / http 测试基建；若无现成基建，至少对 `verify_artifact` 后的赋值分支做断言。
