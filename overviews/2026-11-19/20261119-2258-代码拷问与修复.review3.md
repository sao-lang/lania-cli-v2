## 上一轮 findings 逐条回应

### [Should] webpack build 编译错误（`stats.errors` 非空）仍被判成功 → 已正确修复 ✓

本轮在 webpack.ts:339-342 给 build result 补了 `success: errors.length === 0`，并在 `errors.length > 0` 时展开 `error`。差分核实（能区分改动前后）：

- 改动前：result 由 `createCompilerResult` 生成、无 `success` 字段 → Rust `unwrap_or(true)` → `EXIT_SUCCESS`（假成功）。
- 改动后：`errors` 非空时 `success=false`，`error` 含首个错误消息 → Rust `resolve_build_exit_code`（build.rs:29-32）读到 `success=false` → `EXIT_RUNTIME_ERROR`。

且事件侧 `compilerDoneEvent(..., errors.length === 0, ...)`（webpack.ts:302-308）本就是 `success=false`，本次 result 与事件**语义一致**，修法正确。

### [Nit] 新测试未断言错误来源 → 已正确修复 ✓

compiler.test.ts:311-314 补了 `result.error` 含 `'vite boom'` 的断言。核实 `vite.ts:184` 的 catch 文案为 `vite dev failed: ${normalizeError(error).message}`，确实含 `vite boom`；而 worker 层兜底文案为 `runtime adapter unavailable`（compiler.ts:79/115、compiler-worker.ts:121）与 `bridge worker unavailable`（compiler.ts:82/118），均不含 `vite boom`。该断言能有效区分 adapter catch 与 worker 兜底。

## 本轮四个核实点的逐项判定

### 核实点 1：webpack result 的 `success`/`error` 是否真的生效

**生效。** 完整透传链逐环核实：

1. webpack.ts:332-343 把 `success`/`error` 放进 `createCompilerResult` 的第 4 参 `extras`。
2. `createCompilerResult`（compiler-shared.ts:93-102）以 `...extras` **最后展开**，因此 `success`/`error` 写入 result，不被骨架字段覆盖。
3. worker 层 `markWorkerExecution`（compiler-worker-protocol.ts:67-73）以 `...execution.result` 展开，仅追加 `workerMode`/`isolated`，**不丢 `success`/`error`**；`stripActiveCompiler`（compiler-worker.ts:125-130）用对象解构保留其余字段。
4. Rust build.rs:29-32 只读 `result.success`，缺失才 `unwrap_or(true)`；本轮 `success=false` 明确可见 → `EXIT_RUNTIME_ERROR`。

结论：`success:false` 从 adapter 到 CLI 退出码**全程真实生效**，不是写了字段但被上层吞掉。

### 核实点 2：watch 模式下补 `success` 是否引入副作用（长任务误判）

**不引入“误判成功”回归，属净改善；但存在“首轮快照”语义限制（见 Nit-2）。**

- `collectStats()`（webpack.ts:246-256）在 watch 模式走 `compiler.watch`，其回调会在每次重编译时触发，但 Promise 只 `resolve` 第一次 → `stats`/`errors` 是**首轮编译快照**。
- `success` 基于首轮 `errors.length === 0`：首轮编译错误 → `success=false` → 退出码非 0。这符合 fail-fast，**不是误判**。
- watch 是长任务，`activeCompiler` 仍被设置（webpack.ts:310-324）；compiler.ts:108-113 先注册 `activeCompiler` 再返回 result，故即使 `success=false`，后续 `stop` 仍可用，不会出现“失败结果导致长任务无法停止”。
- 改动前 watch 的 result 恒无 `success`（恒判成功）；改动后首轮失败能报错，方向正确。

### 核实点 3：`errors[0]` 类型断言是否安全（元素可能是 string 或 object）

**运行时安全（不崩溃），但 string 形态错误会丢失真实消息。**

webpack.ts:331 `(errors[0] as { message?: unknown })?.message`：

- 类型断言对 `any` 无运行时检查，但后续 `?.message` + `typeof firstError === 'string'`（:341）构成保护：元素为 string/number/object（无 message）/null 时，`.message` 均为 `undefined`，**不会抛异常**，`success` 仍由 `errors.length === 0` 正确判定，fail-fast 不受影响。
- 但 webpack 某些错误形态为纯字符串时，`firstError=undefined` → `error` 退化为通用串 `'webpack build failed'`（:341），丢失真实定位信息。这与同文件:294/:299 处理 issue/warning 时采用的健壮写法 `typeof item?.message === 'string' ? item.message : JSON.stringify(item)` 不一致。定为 Nit-1，非 Blocker/Should。

### 核实点 4：两个新测试是否真实锁定改动 / 是否破坏既有测试

**均真实锁定改动（非假绿），既有测试未被破坏。**

## 可选（Nit，最多 3 条）

### [Nit] webpack build `error` 文案在 string 形态错误时退化为通用串

- **文件:行号**：`packages/foundation/bridge-slices/compiler/ts/src/plugins/compiler-adapters/webpack.ts:331, 340-342`（对照同文件:294/:299）。
- **现象**：`(errors[0] as { message?: unknown })?.message` 在错误元素为纯字符串时得到 `undefined`，`error` 退化为 `'webpack build failed'`，丢失真实消息。
- **后果**：仅影响诊断文案保真度；`success=false` 与退出码不受影响，不构成 fail-fast 残留。
- **改法**：复用同文件:294 的健壮写法，例如：
  ```ts
  const raw = errors[0];
  const message =
    typeof (raw as any)?.message === 'string'
      ? (raw as any).message
      : typeof raw === 'string'
        ? raw
        : JSON.stringify(raw);
  // error: message
  ```

### [Nit] watch 模式 `result.success` 为首轮快照，不随增量编译更新

- **文件:行号**：`.../compiler-adapters/webpack.ts:246-256, 339`；消费侧 `packages/commands/workspace/rust/src/build.rs:28-38`。
- **现象**：`compiler.watch` 回调虽每次重编译触发，但 Promise 只 resolve 首次；`success` 因此固定为首轮结果。首轮成功、后续改坏时 `success` 恒为 `true`；首轮失败、后续修好时恒为 `false`。
- **后果**：`build --watch` 最终退出码反映首轮而非最终编译状态。属 watch 长任务语义的固有局限（改动前连 `success` 都没有、恒判成功），本轮为净改善，非回归。
- **改法**：若要精确，可在 `activeCompiler.stop()` 内重取最后一次 stats 的 errors 覆写 result（需 Rust 侧支持长任务退出码在 stop 时定稿）；否则在注释中明确“watch 的 success 表示首轮编译状态”。

## 综合三报告：Blocker 级“web 失败被判成功”残留扫描

对决定 CLI 退出码的 **build 主路径**逐工具核对：

| 工具/分支                                    | 失败触发                                   | result `success`                                              | 判定 |
| -------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------- | ---- |
| webpack build catch（工具抛错）              | `compiler.run/watch` 回调 error / 启动异常 | `failureExecution` → `false`                                  | ✓    |
| webpack build `stats.errors`（编译错误不抛） | `toJson().errors` 非空                     | 本轮补 `success:false`                                        | ✓    |
| vite build                                   | `runtime.build()` reject → catch           | `failureExecution` → `false`                                  | ✓    |
| rollup build                                 | `bundle.write()` reject → catch            | `failureExecution` → `false`                                  | ✓    |
| nest/tsc build                               | 工具缺失                                   | `failureExecution` → `false`（有测试 248-270）                | ✓    |
| webpack dev 缺 dev-server                    | 保留结构                                   | `success:false` + `error`（webpack.ts:75-98，上轮已核实生效） | ✓    |

build 主路径已无“失败被判成功”残留。

**dev 长任务边角**（rollup watch ERROR/1500ms 超时仍报成功，第二轮 Nit；vite dev 运行期改坏代码）不是 Blocker：`resolve_dev_exit_code`（dev.rs:29-39）虽同样读 `success`，但 dev 为长驻任务，退出码在 stop/结束才产生，且 dev 的 fail-fast 主要靠“不伪造 `server_ready`/`dev_url` 事件”实现，上层不会显示假 URL；这些边角不会造成“用户看到构建成功 + 假产物 + 退出码 0”的 Blocker 后果，沿用第二轮 Nit 定级。

**结论：三轮报告合并，未发现 Blocker 级“web 失败被判成功”残留。**
