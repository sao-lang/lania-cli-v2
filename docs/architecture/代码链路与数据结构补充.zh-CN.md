## 1. 启动全链路（逐层拆解）

### 1.1 npm wrapper → Rust 二进制

**文件**：`npm/cli/bin/lan.mjs`

```
用户输入 `lan dev`
  → resolveRuntimeLayout() 判断是 development 还是 installed 模式
  → 找到平台二进制路径（debug/release 或 @lania-cli/cli-darwin-arm64 等）
  → spawn(binaryPath, process.argv.slice(2), {
       env: {
         LANIA_NODE_BRIDGE_DIR,   // Node bridge 载荷目录
         LANIA_PRODUCT_ROOT,      // 产品根目录
         LANIA_RUNTIME_MODE,      // "development" | "installed"
       }
     })
  → 子进程退出时透传 exit code / signal
```

关键设计：npm wrapper **不参与任何命令解析**，只做"找二进制、设环境变量、spawn"三件事。

### 1.2 Rust 入口 → 命令树构建

**文件**：`rust/crates/lania-cli/src/main.rs`

```
main():
  1. HostRuntime::new()                    ← 创建空宿主
  2. host.register_plugin(x12)             ← 注册 12 个命令插件（顺序决定 --help 展示顺序）
  3. host.initialize().await               ← 生命周期: discover → resolve → load → plugin_setup → runtime_start
  4. load_lan_config_snapshot_from_cwd()   ← 加载项目配置（best-effort）
  5. bootstrap_project_extensions()        ← 通过 Node bridge 解析动态命令 → 注册到命令树
  6. 构建 output_profile（json/jsonl/human + spinner/bar/none + locale）
  7. attach_logger_sink() / attach_progress()
  8. 处理内建命令（--help/--version）→ 短路返回
  9. build_cli(commands) → clap.try_get_matches_from(argv)  ← 构建并解析 clap 命令树
  10. command_context_from_matches()       ← 将 clap matches 转为 CommandContext
  11. host.execute_command(&context)       ← 交给 HostRuntime 执行
  12. host.shutdown_async()                ← 关闭 Node bridge、清理资源
  13. 输出结果 JSON 到 stdout
```

### 1.3 HostRuntime 初始化内部

**文件**：`rust/crates/lania-host/src/runtime.rs` + `rust/crates/lania-host/src/runtime/lifecycle.rs`

```
HostRuntime::initialize():
  → lifecycle_discover()     ← 发现插件、收集 meta
  → lifecycle_resolve()      ← 解析插件依赖顺序（before/after）
  → lifecycle_load()         ← 加载配置
  → bootstrap_host_capabilities()  ← 注册 exec/fs/git/pm/prompt/progress/task/logger 等宿主能力
  → plugin.setup_all()       ← 调用每个插件的 setup() → 注册 CommandSpec + handler + hooks + capabilities
  → runtime_start()          ← 启动 Node bridge 子进程 + 握手
  → 生成 runtime summary
```

### 1.4 Node Bridge 握手

```
Rust (NodeBridgeClient)              Node (stdio.ts)
  │ 写入 stdin: { type: "handshake",     │
  │   payload: { protocolVersion, ... } } │
  │                                     │ 读取 stdin 行
  │                                     │ 写入 stdout: { type: "event",
  │                                     │   requestId: "bridge",
  │                                     │   payload: { method: "event.ready",
  │                                     │     params: { plugins: [...] } } }
  │ 读取 stdout 行 ←─────────────────────┤
  │                                     │
  │                                     │ 写入 stdout: { type: "handshake",
  │                                     │   payload: { protocolVersion,
  │                                     │     bridgeName, methods[], events[],
  │                                     │     heartbeatIntervalMs, ... } }
  │ 读取 stdout 行 ←─────────────────────┤
  │ 握手完成                             │ 启动心跳定时器（heartbeatIntervalMs）
  │                                     │
  │ 后续: 每 heartbeatIntervalMs 收到    │
  │   { type: "event", requestId: "bridge",
  │     payload: { method: "event.heartbeat",
  │       params: { ts } } }
```

握手完成后双方进入正常通信状态。

## 2. 命令执行链路（三类路径）

### 2.1 Bridge 型命令（dev / build / lint）

以 `lan dev` 为例：

```
lan dev
  → main.rs: clap 解析 → CommandContext { handler_id: "command.dev" }
  → HostRuntime::execute_command()
  → 查 handler registry → DevCommandHandler
  → DevCommandHandler.execute():
      1. require_capability(NodeBridge)
      2. 构造 BridgeRequest { method: "compiler.dev", params: { cwd, port } }
      3. ctx.call_bridge(request)
  → NodeBridgeClient::call():
      1. 生成 request_id
      2. 注册 pending 表 (event_tx, response_tx)
      3. 写入 stdin: { type: "request", payload: { id, method: "compiler.dev", params } }
  → Node stdio.ts 收到:
      1. handleExchange() → plugin-dispatch.ts → 路由到 compiler plugin
      2. compiler plugin 执行 dev server
      3. 期间发送事件: event.compiler_server_ready, event.compiler_asset, event.log 等
      4. 最终发送 response { id, result }
  → Rust reader 线程收到:
      1. event → 转发到对应 event_tx → HostRuntime 处理事件（日志、进度等）
      2. response → 通过 response_tx 完成 BridgeExchange
  → DevCommandHandler 收到 exchange，构造 CommandExecution::Bridge
```

关键点：Bridge 型命令的**事件流是流式的**，Rust 侧边收事件边渲染，不等最终 response 才展示。

### 2.2 Workflow 型命令（create / release / generate / sync）

以 `lan create` 为例：

```
lan create --name demo --template spa-react
  → CommandContext { handler_id: "command.create" }
  → CreateCommandHandler.execute():
      1. require_capability(Template)
      2. emit_workflow_start("create")
      3. CreateWorkflow::run(ctx)
         Phase 1 - 采集输入:
           a. TemplateCapability::list() → bridge.list_templates()
           b. run_create_prompt() → 交互式提问
           c. TemplateCapability::questions() → 模板专属问题
           d. run_template_prompt()
         Phase 2 - 生成计划:
           e. TemplateCapability::dependencies()
           f. hooks.call_waterfall("dependencies_modify")
           g. resolve_dependency_versions()
           h. TemplateCapability::output_tasks()
           i. TemplateCapability::render() → 返回 Vec<PlannedFile>
           j. hooks.call_waterfall("template_parse")
         Phase 3 - 落地执行:
           k. format_planned_files()
           l. hooks.call_waterfall("files_prepare")
           m. write_files_with_hooks()  ← 真正写盘，per-file before/after hook
           n. package_manager.install()
           o. git.init()
           p. 构造 WorkflowExecution 返回
      4. 构造 CommandExecution::Workflow
```

核心设计：**模板语义在 Node，事务控制（写盘）在 Rust**。Node 返回"文件计划"，Rust 决定"写不写、怎么写"。

### 2.3 动态命令（项目自定义）

```
项目在 lania.schemas.ts 中声明:
  { name: 'deploy', options: [...], prompt: [...], workflow: 'deploy' }

启动时:
  1. bootstrap_project_extensions() → bridge 调 commands.resolveDynamic
  2. Node 侧解析 schema → 返回 commands[] + handlers[]
  3. Rust 侧注册到 CommandRegistry → 挂入 clap 命令树

执行时:
  4. clap 解析 → handler_id 指向动态命令
  5. HostRuntime 查 handler → 发现是动态命令 handler
  6. 构造 BridgeRequest { method: "command.invokeDynamic", params: { ... } }
  7. Node 侧 runDynamicExecutor():
     - type === "local": 直接调用内存态 handler 函数
     - type === "manifest": 加载插件 → plugin.handle()
  8. 返回执行结果
```

## 3. 核心数据结构全景

### 3.1 Rust 侧关键结构

```
CommandSpec              ← 命令"长什么样"（纯声明，无执行逻辑）
  ├── name: String
  ├── about: String
  ├── alias / aliases
  ├── args: Vec<ArgSpec>          ← 位置参数
  ├── options: Vec<OptionSpec>    ← 命名选项（--xxx）
  ├── examples: Vec<Example>
  ├── subcommands: Vec<CommandSpec>
  └── handler_id: String          ← 指向实际执行者

CommandContext            ← "解析完成、准备执行"的命令快照
  ├── cwd: String
  ├── argv: ParsedArgv
  │     ├── args: BTreeMap<String, Value>     ← 位置参数
  │     └── options: BTreeMap<String, Value>  ← 命名选项
  ├── handler_id: String
  └── trace_id: String

CommandExecutionContext  ← 执行期的"运行时背包"
  ├── 所有宿主能力引用: exec, fs, git, pm, prompt, progress, tasks, logger, node_bridge
  ├── hooks: Arc<dyn HookRuntime>
  ├── project_config: Option<LanConfigSnapshot>
  └── locale

CommandExecution         ← 统一结果枚举
  ├── Bridge { context, request, exchange, follow_up, exit_code }
  ├── Workflow { context, execution: WorkflowExecution, exit_code }
  └── TemplateInfo { context, output, exit_code }

WorkflowExecution        ← 一次工作流的完整快照
  ├── workflow: String           ← "create" | "add" | "release" | "sync" | "generate"
  ├── state: WorkflowState       ← 8 阶段状态机
  ├── target_dir: String
  ├── prompts: BTreeMap<String, Value>
  ├── bridge_steps: Vec<WorkflowBridgeStep>
  ├── written_files: Vec<String>
  ├── conflicts: Vec<String>
  ├── command_plans: Vec<Vec<String>>
  ├── git_status: Option<GitStatus>
  └── notes: Vec<String>

WorkflowState 状态机:
  Planned → Prompted → Rendered → FilesWritten → CommandsPlanned → GitReady → Completed
                                  ↘              ↘
                                    Failed         Failed

PluginMeta                 ← 插件元信息
  ├── name, version
  ├── kind: PluginKind (Rust | Node)
  ├── requires: Vec<CapabilityName>
  ├── before: Vec<String>         ← 排序：在哪些插件之前
  └── after: Vec<String>          ← 排序：在哪些插件之后
```

### 3.2 Node 侧关键结构

```typescript
// 协议层
BridgeRequest { id, method, params }
BridgeResponse { id, result?, error? }
BridgeEvent { method, params }
HandshakeRequest { protocolVersion, transport, encoding, hostName }
HandshakeResponse { protocolVersion, bridgeName, methods[], events[], heartbeatIntervalMs, ... }

// 动态命令
RuntimeContext { mode, traceId, invocationCwd, workspaceRoot, productRoot, schemaRoot }
ProductContext { name, binaryName, displayName, version, productRoot, schemaRoot, templatesDir }

ScaffoldPlan {                    ← 脚手架执行计划
  preset: string | null,
  features: string[],
  templateLayers: string[],
  dependencyRecipes: string[],
  dependencies: string[],
  devDependencies: string[],
  scripts: Record<string, string>,
  packageManager: string | null,
  resolvers: Record<string, ScaffoldResolverPlan>,
  mergeRules: ScaffoldMergeRulePlan[],
  guards: ScaffoldGuardPlan[],
  postActions: ScaffoldPostActionPlan[],
}

// 模板
TemplateManifest {                ← template.json 清单
  name, schemaVersion, renderEngine,
  legacyTemplateDir, ownership, useCases, migrationLayer?
}

TemplateFileRule {                ← 文件规则
  outputPath: string,             // 如 "src/index.ts"
  templatePath?: string,          // 默认映射到 files/<outputPath>.ejs
}
```

### 3.3 Bridge 协议消息格式

```
Rust → Node (stdin):
  {"type":"handshake","payload":{protocolVersion,transport,encoding,hostName}}
  {"type":"request","payload":{id,method,params}}
  {"type":"host_response","payload":{id,result?,error?,events[]}}

Node → Rust (stdout):
  {"type":"event","requestId":"bridge"|requestId,"payload":{method,params}}
  {"type":"handshake","payload":{protocolVersion,bridgeName,methods[],events[],...}}
  {"type":"response","payload":{id,result?,error?}}
  {"type":"host_request","payload":{id,method,params}}
```

**关键约束**：

1. stdout **只能**输出协议 envelope，不能有 `console.log`
2. 同一个 request 的 events **必须先于** response 发出
3. `host_request` 和 `request` 共用同一管道，互不阻塞

## 4. Host RPC 反向调用链路

当 Node 侧动态命令或插件需要调用宿主能力时：

```
Node (schema handler / workflow)
  → hostCall("host.exec.run", { cwd, program, args, __toolsPolicy })
  → 生成 host_request { id, method: "host.exec.run", params }
  → stdio.ts: 写入 stdout: { type: "host_request", payload }
  →
  Rust reader 线程收到:
  → 识别为 host_request → 交 HostRpcAdapter.handle()
  → dispatch_host_rpc(method, payload, tools_policy):
       ├── host.exec.*  → handle_exec_domain()  ← 检查 allowShell / allowEnvWrite
       ├── host.fs.*    → handle_fs_domain()    ← 检查 writeRoot
       ├── host.git.*   → handle_git_domain()
       ├── host.pm.*    → handle_pm_domain()
       ├── host.log.*   → handle_log_domain()
       ├── host.tasks.* → handle_tasks_domain()
       ├── host.progress.* → handle_progress_domain()
       └── host.interaction.* → handle_interaction_domain()
  → audit_tool_call()  ← TRACE 级别审计
  → 写入 stdin: { type: "host_response", payload: { id, result, events } }
  →
  Node 收到:
  → handleHostResponse() → resolve pending promise
  → 动态命令继续执行
```

**安全策略传递**：`__toolsPolicy` 从 `lan.config.json` 的 `tools` 段传入：

```json
{
  "tools": {
    "exec": { "allowShell": false, "allowEnvWrite": false },
    "fs": { "writeRoot": "./project-dir" }
  }
}
```

## 5. 产品化闭环内部实现

### 5.1 lan product build

```
Rust: BuildCommandPlugin
  → 构造 BridgeRequest { method: "product.build", params: { outputDir } }
  → Node: product plugin
  → 读取 product/lania.schemas.ts + product/templates/
  → 编译、校验、生成 product snapshot
  → 写入 .lania/build/product/ 目录
  → 返回结果
```

### 5.2 lan product pack

```
Rust: BuildCommandPlugin
  → BridgeRequest { method: "product.pack", params: { buildDir, outputDir } }
  → Node: product plugin
  → 读取 build 产物
  → 组装 install-root 布局:
      bin/lan                    ← npm wrapper
      lib/node-bridge/           ← Node bridge payload
      lib/templates/             ← 模板资产
      platform-packages/         ← 各平台二进制
  → 写入 .lania/pack/product/install-root/
  → 返回结果
```

### 5.3 lan product publish

```
Rust: BuildCommandPlugin
  → BridgeRequest { method: "product.publish", params: {
      packDir, outputDir, distTag, channel, registry,
      npmBin, maxRetries, rollbackOnFailure, execute, dryRun
    }}
  → Node: product plugin
  → 读取 pack 产物
  → 组装 npm 发布包:
      package.json, bin/, lib/, README.md, LICENSE
  → 写入 .lania/publish/product/npm-package/
  → 如果 execute=true: 执行 npm publish（带重试、回滚策略）
  → 如果 dryRun=true: 只生成 publish manifest，不实际发布
  → 返回结果
```

## 6. 模板渲染内部流水线

### 6.1 模板目录结构

```
my-template/
  template.json          ← 清单（name, renderEngine, ownership, useCases）
  questions.js           ← 动态问题（可选）
  dependencies.js        ← 动态依赖（可选）
  config.js              ← 动态文件规则（可选，返回 TemplateFileRule[]）
  files/
    src/index.ts.ejs     ← EJS 模板
    package.json.ejs
```

### 6.2 渲染流程（Node 侧）

```
TemplateCapability::render(template, context)
  → loadTemplateConfig(template, input)    ← 加载 config.js → 获取 files[]
  → 如果 config 不返回 files: 扫描 files/**/*.ejs → 去掉 .ejs 后缀作为 outputPath
  → buildTemplateLocals(context, options)  ← 合并上下文 + 补齐默认值
    补齐的默认值: projectName, useTs, lintTools, cssTools, buildTool,
                 packageManager, repository, unitTestTool, port 等
  → 对每个 fileRule:
      ejsRenderer.renderFile(templateFilePath, locals)
      → 使用 ejs 库（async: true）
      → 返回 { path: outputPath, content: string }
  → 返回 { template, schemaVersion, renderEngine, files: [{path, content}] }
```

### 6.3 Rust 侧网关模式

```
TemplateCapability (Rust):
  list()         → bridge.list_templates()       │ fallback: declared_template_names()
  questions()    → bridge.get_template_questions() │ fallback: declared_template.questions
  dependencies() → bridge.get_template_dependencies() │ fallback: declared_template.dependencies
  output_tasks() → bridge.get_template_output_tasks() │ fallback: declared_template.output_tasks
  render()       → bridge.render_template()       │ fallback: render_declared_template()
```

每个方法返回 `(结果, Option<WorkflowBridgeStep>)`，让 workflow 层可以记录 bridge 交互轨迹。

## 8. 关键 Hook 点

| Hook Key              | 触发时机       | 模式      | 用途                 |

## 10. 面试常问题：设计权衡（Trade-offs）

> 这一节是面试时最可能被追问的内容。建议每个 trade-off 都准备一个"当时为什么这么选"的故事。

### 10.1 为什么选 Rust + Node.js 双运行时，而不是纯 Rust 或纯 Node？

**不选纯 Rust 的原因**：

- JS 生态的编译器（Vite/Webpack）、模板引擎（EJS）、npm 包管理无法绕开
- 用 Rust 重写这些轮子不现实，也不值得

**不选纯 Node 的原因**：

- CLI 需要强类型命令树解析、统一输出格式、审计兜底——Rust 更擅长
- 插件安全模型在 Node 侧做"真沙箱"很困难，Rust 侧做策略强制执行更可控

**实际收益**：Rust 管控制和治理，Node 管生态和扩展，各取所长。

### 10.2 为什么选 STDIO JSON-RPC，而不是 gRPC 或 Unix Socket？

| 方案            | 问题                                                       |
| --------------- | ---------------------------------------------------------- | --------------------------- |
| **gRPC**        | 引入 protobuf 编译依赖，跨平台分发成本高，调试需要额外工具 |
| **Unix Socket** | Windows 支持差，命名管道 API 不统一                        |
| **TCP**         | 端口冲突、防火墙、安全性问题                               |
| **STDIO**       | 跨平台一致、零额外依赖、调试方便（`cat log                 | jq`）、进程生命周期自然绑定 |

**代价**：stdout 只能输出协议 envelope，不能有 `console.log`，调试时需要用 `--trace` 走 stderr。

### 10.3 为什么 Node 要能反向调用 Rust（Host RPC），而不是直接在 Node 侧执行？

**直接在 Node 侧的风险**：

- Node 子进程权限不受限 → 恶意插件可以 `exec("rm -rf /")`
- 文件系统写操作绕过 Rust 的 hooks 和事务控制

**Host RPC 方案的好处**：

- 所有风险操作（exec/fs/git）必经 Rust 侧策略引擎
- `lan.config.json` 的 `tools` 段可以声明 `allowShell: false`、`writeRoot: ./project`
- 审计日志统一在 Rust 侧收口

**实际案例**：插件调用 `host.fs.write` 时，Rust 会检查目标路径是否在 `writeRoot` 内，不在则返回 `[E_TOOLS_DENIED]`。

### 10.4 为什么把模板渲染放在 Node，写盘放在 Rust？

**Render in Node**：EJS 是 JS 生态的模板引擎，Node 侧天然支持；Rust 侧虽能用 `tera` 等库，但项目如果已有 JS 模板资产，迁移成本高。

**Write in Rust**：写盘是"不可逆操作"，需要 hooks 拦截、冲突检查、事务控制。Rust 侧 `write_files_with_hooks()` 在每个文件写前/写后都触发 hook，允许插件拦截和改写。Node 侧如果直接写盘，这些治理点就绕过了。

### 10.5 为什么插件安全模型要用三层裁剪，而不是一层？

```
声明 methods → 插件实际导出 methods → policy.allowedMethods → 最终可用 methods
```

三层设计对应三个独立变化维度：

- **声明**：项目作者说了"我想用这些方法"
- **实际**：插件开发者说了"我提供了这些方法"
- **策略**：管理员说了"允许用这些方法"

三者的交集才是最终可用方法。这样即使插件声明了危险方法、项目配置了它，只要策略层不允许，仍然不可用。

### 10.6 为什么选 clap 做命令解析，而不是手写解析器？

- clap 是 Rust CLI 事实标准，社区成熟
- 支持自动生成 `--help`、自动补全、错误提示
- `CommandSpec → clap` 的映射层，把"命令声明"和"命令解析"解耦
- 如果需要切换解析器（如 `clap` → `gum`），只需修改 `lania-command/src/parser.rs` 一个文件

## 11. 面试常问题：对比现有方案

### 11.1 和 oclif / commander 相比

| 维度       | oclif / commander | lania-cli                        |
| ---------- | ----------------- | -------------------------------- |
| 运行时     | 纯 Node           | Rust + Node 双运行时             |
| 命令树     | 运行时动态构建    | Rust 编译期构建 + 运行时动态扩展 |
| 输出格式   | 默认文本          | 内置 json/jsonl/human 三种模式   |
| 插件安全   | 无内置模型        | 三层裁剪 + Host RPC 策略         |
| 产品化     | 无内置支持        | 内置 build/pack/publish 管线     |
| 状态工作流 | 无                | WorkflowExecution 状态机         |
| 跨语言     | 仅 JS             | Rust 命令 + JS 扩展              |

**核心差异**：oclif 是"Node CLI 框架"，lania-cli 是"可以挂 Node 插件的 Rust CLI 宿主"。定位不同，面向的场景也不同。

### 11.2 和 cargo / pnpm 的 CLI 插件架构相比

- **cargo**：插件是独立二进制，通过 `cargo-xxx` 命名约定发现，无安全模型
- **pnpm**：插件是 npm 包，通过 hooks 扩展生命周期，安全靠 npm 生态
- **lania-cli**：插件分两层（Rust Plugin + Node Bridge Plugin），三层安全裁剪。Rust 层管治理，Node 层管生态

### 11.3 为什么不直接用 oclif 然后加 Rust 模块？

- oclif 的插件模型和生命周期是 Node 原生的，加入 Rust 模块后无法享受 oclif 的治理能力
- 双运行时不是"在 CLI 框架上绑一个 Rust 模块"，而是"Rust 做宿主、Node 做扩展"——这是倒过来的架构

## 12. 面试常问题：失败场景与边界情况

### 12.1 Node bridge 进程崩溃怎么办？

- Rust 侧 reader 线程发现 stdin 断开 → `MapError` → 返回 `BridgeError`
- 调用方（workflow / handler）收到 error 后回退或报错
- 配置 `failure_strategy: "reconnect"` 时可自动重启 bridge 进程

### 12.2 模板渲染失败怎么处理？

- Node 侧 `ejs.renderFile()` 抛出异常 → BridgeResponse.error
- Rust 侧 `WorkflowExecution.state = Failed`
- 已写入的文件不会自动回滚（当前设计：写盘前会先做冲突检查，但写了一半不撤销）
- 改进方向：`transaction-engine.ts` 支持 rollback，目前还在草案阶段

### 12.3 动态命令和内置命令同名会怎样？

- CLI 构建时先注册内建命令，再挂载动态命令
- `CommandRegistry` 实现中，同名命令以**首次注册为准**（先到先得）
- 因此动态命令不会覆盖内置命令，但会收到 warning

### 12.4 项目配置（lan.config.\*）加载失败会怎样？

- 配置加载是 **best-effort**：失败时不阻塞 CLI 启动
- 动态命令和项目插件会降级为"不可用"
- 内置命令（dev/build/lint/create 等）仍然正常工作
- 错误信息通过 logger 输出，但不影响 exit code

## 14. 这个项目不做的事情

> 面试官问你"还有什么要考虑的"，主动说出项目边界比被动回答更有深度。

1. **不做 JS 工具链（编译器/linter）的实现**——只做桥接，不做实现
2. **不做大规模文件同步**——`lan sync` 基于 git，不做 rsync 级别的文件同步
3. **不做包管理器**——`lan pm` 基于 npm/pnpm/yarn/bun，不做自己的 registry
4. **不做独立模板市场**——模板来源当前限本地文件和打包资产
5. **不做完全的热插拔**——动态命令在启动时解析注册，运行中不可新增
6. **不做浏览器/IDE 集成**——纯命令行工具
7. **不做 Windows 以外的平台二进制分发**——当前仅 darwin-arm64 / linux-x64 有平台包
