# 04 请求构造与流式调用：传输与协议的解耦

这篇讲两个相关但独立的设计：

1. **请求构造如何脱离传输层**——命令层只生成 `BridgeRequest`（纯数据），不持有任何连接/进程状态。
2. **事件如何做到实时流式**——`call_stream` 让 agent 的逐 token 输出边生成边渲染，而不是等命令跑完一次性回放。

## §1 问题：命令层真的需要 NodeBridgeClient 吗？

Hub 单轨化后，所有执行都走 `provider.call`。但命令代码里还散布着大量这样的调用：

```rust
let request = build_request(ctx.command(), ctx.node_bridge());
let run = ctx.call_bridge(request).await?;
```

`ctx.node_bridge()` 返回的是 `NodeBridgeClient`——一个持有子进程、reader task、事件通道、metrics 的重量级对象。可命令层只是用它调 `request()` 构造一个请求对象，**真正的执行是 `call_bridge` 通过 Hub 完成的**。

看 `NodeBridgeClient::request()` 的实现（`lania-node-bridge/src/client/transport/requests.rs:78`，改造前）：

```rust
pub fn request(&self, method: impl Into<String>, params: Value) -> BridgeRequest {
    let id = format!("req-{}", self.sequence.fetch_add(1, Ordering::SeqCst) + 1);
    BridgeRequest { id, method: method.into(), params }
}
```

**纯粹的构造逻辑，零状态依赖**（除了一个递增计数器）。让命令层为了构造一个三字段结构体而持有一个 bridge client，是明显的设计泄漏。

## §2 BridgeRequest::new：把 id 生成提到协议层

**`lania-node-bridge/src/protocol.rs`**：

```rust
/// 进程内单调递增的请求 id 计数器。
static REQUEST_SEQUENCE: AtomicU64 = AtomicU64::new(0);

impl BridgeRequest {
    /// 构造一条请求：id 进程内单调递增，格式 `req-N`。
    pub fn new(method: impl Into<String>, params: Value) -> Self {
        let id = format!("req-{}", REQUEST_SEQUENCE.fetch_add(1, Ordering::SeqCst) + 1);
        Self { id, method: method.into(), params }
    }
}
```

`NodeBridgeClient::request()` 改为委托它，并删掉 client 自己的 `sequence` 字段——**全局只有一套 id 生成器**，格式 `req-N` 保持不变（reader 路由、日志都依赖这个格式）。

## §3 RequestFactory + Deref：一套实现，两种用法

`requests.rs` 里原本有 20 个语义化请求构造器（`lint_run_request`、`compiler_build_request`、`system_list_commands_request`、`template_list_request` …），都是 `impl NodeBridgeClient` 的方法。它们把 method 名和 params 结构集中收口——这是好设计，不该丢。

做法：把这 20 个方法从 `impl NodeBridgeClient` 提取到 **零大小结构体 `RequestFactory`**（`protocol.rs`），然后让 `NodeBridgeClient` 通过 `Deref` 复用：

```rust
/// 纯请求构造器：只生成 BridgeRequest，不持有连接/进程状态。
#[derive(Debug, Clone, Copy, Default)]
pub struct RequestFactory;

impl RequestFactory {
    pub fn request(&self, method: impl Into<String>, params: Value) -> BridgeRequest {
        BridgeRequest::new(method, params)
    }
    pub fn lint_run_request(&self, cwd: impl Into<String>, fix: bool, concurrency: Option<usize>) -> BridgeRequest {
        self.request("lint.run", json!({ "cwd": cwd.into(), "fix": fix, "concurrency": concurrency }))
    }
    // ... 其余 19 个
}
```

**`client.rs` 的 Deref**：

```rust
/// 语义化请求构造通过 Deref 复用 `RequestFactory` 的纯实现：
/// `client.lint_run_request(..)` 与 `RequestFactory.lint_run_request(..)` 是同一份代码，
/// 协议知识只有一处。
impl std::ops::Deref for NodeBridgeClient {
    type Target = RequestFactory;
    fn deref(&self) -> &Self::Target {
        const FACTORY: &RequestFactory = &RequestFactory;
        FACTORY
    }
}
```

**效果**：

- 命令层用 `ctx.request_factory().lint_run_request(...)`——纯构造，不碰 client。
- `NodeBridgeClient` 内部（capabilities.rs、测试）继续用 `client.lint_run_request(...)`——通过 Deref 落到同一个实现，无需改动。
- 协议知识（method 名、params 结构）**只有一份**。

**`ctx.request_factory()`**（`lania-host/src/execution/context.rs:250`）：

```rust
/// 纯请求构造器：命令层用它生成 BridgeRequest（method/params/id），
/// 执行走 `call_bridge` / `call_runtime_bridge` 的 Hub 单轨。
/// 不暴露 NodeBridgeClient 的连接/进程能力。
pub fn request_factory(&self) -> &lania_bridge_host::node_bridge::RequestFactory {
    self.node_bridge
}
```

命令层 12 处 `ctx.node_bridge()` 全部改为 `ctx.request_factory()`，函数签名 `&NodeBridgeClient` → `&RequestFactory`。测试里用 `RequestFactory::default()` 代替 `NodeBridgeClient::new(...)`。

> 附带成果：pi 的 agent 会话原本是最后一条真实使用 `client.call_async()` 的 1:1 路径，改造后也不再持有 `NodeBridgeClient`（见 §5）。

## §4 call_stream：从"收集后回放"到"边到边回调"

**问题**：`call()` 返回 `BridgeProviderExchange { result, events }`——事件是收集完的。但 agent 的 `prompt` 要逐 token 渲染：token 事件一边生成一边显示，不能等整个回答生成完再一次性打印。

**接口设计** — `lania-host-core/src/lib.rs:84` 给 `BridgeProvider` 加 `call_stream`，默认实现是"先收集再回放"（兼容 Stub 等简单实现）：

```rust
async fn call_stream(
    &self,
    method: &str,
    params: Value,
    on_event: &mut (dyn FnMut(BridgeProviderEvent) + Send),
) -> anyhow::Result<Value> {
    let exchange = self.call(method, params).await?;
    for event in exchange.events { on_event(event); }
    Ok(exchange.result)
}
```

**Hub 覆盖** — `provider.rs:201` `call_sync_stream()` 是真正的实时实现。关键区别：`call_sync`（`:194`）把事件收集进 Vec，而 `call_sync_stream` 在 pump 循环里**刚收到 Event 帧就立即回调**：

```rust
238→  while let Some(frame) = state.client.try_recv() {
239→      match frame {
             BusFrame::Response { id: response_id, .. } => {
                 if response_id == id { outcome = Some((result, error)); }
             }
240→          BusFrame::Event { topic, payload, .. } => {
241→              on_event(BridgeProviderEvent::new(topic, payload));   // 立即回调，不等 response
242→          }
         }
     }
```

`call_sync` 现在是 `call_sync_stream` 的薄包装：

```rust
fn call_sync(&self, method: &str, params: Value) -> Result<BridgeProviderExchange> {
    let mut events = Vec::new();
    let result = self.call_sync_stream(method, params, &mut |event| events.push(event))?;
    Ok(BridgeProviderExchange::new(result, events))
}
```

一处实现，两种消费方式——需要实时回调的走 `call_stream`，需要批量事件的走 `call`。

> 长任务（response 先返回、事件后到）用 `drain_events()`（`provider.rs:343`）在等待期间持续泵事件，是同一思路的另一个入口。

## §5 Agent 会话接入 Hub：流式渲染的完整闭环

**`commands/pi/rust/src/bridge.rs:22` `BridgeAgentSessionClient`** 现在持 provider 而非 client：

```rust
#[derive(Clone)]
pub struct BridgeAgentSessionClient {
    provider: Arc<dyn BridgeProvider>,
    factory: RequestFactory,
}
```

**`prompt()`（`:46`）** 是流式的关键：

```rust
async fn prompt(&self, request: PromptRequest, on_event: &mut EventSink<'_>) -> Result<PromptOutcome> {
    let bridge_request = self.factory.request("agent.prompt", request.params());
    let result = self.provider.call_stream(
        &bridge_request.method,
        bridge_request.params,
        &mut |event: BridgeProviderEvent| {
            if let Some(parsed) = AgentEvent::from_method(&event.method, &event.params) {
                on_event(parsed);
            }
        },
    ).await?;
    Ok(prompt_outcome_from_result(&result))
}
```

**逐 token 的完整链路**：

```
Node 插件 emit event.agent_text_delta
  → publish 帧 → Hub broadcast → host 端点 event 帧
  → call_sync_stream 立即回调 BridgeProviderEvent
  → AgentEvent::from_method("event.agent_text_delta", ...) → TextDelta { delta }
  → on_event 渲染到终端（此时 agent 的 response 还没返回）
```

其他方法（`create/interrupt/state/models/close`）都是普通 `provider.call`——它们没有流式需求。

**handler 侧**（`commands/pi/rust/src/handler.rs:83`）：

```rust
let provider = ctx.bridge_provider()
    .ok_or_else(|| anyhow::anyhow!("hub bridge provider is not attached (no 1:1 fallback)"))?
    .clone();
let client = bridge_client(provider, ctx.request_factory().clone());
```

拿不到 provider 直接报错——和主链路一样，没有 1:1 回落。

## 一句话总结

请求构造与执行被彻底解耦：**`RequestFactory` 只生成数据（method/params/id），`BridgeProvider` 只负责执行**，两者通过 `BridgeRequest` 这个纯数据结构连接。事件消费有两条路：`call` 收集后批量处理，`call_stream` 边到边实时回调——后者让 agent 逐 token 渲染成为可能。这套解耦让命令层完全不知道对面是 Node、Python 还是 Go，也不知道底下有没有真实的子进程。
