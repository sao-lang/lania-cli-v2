# Bridge Hub 深度精讲：总览与学习推荐

这一组文档逐行精讲「Hub 单轨化」之后的核心代码。它回答两个最主要的问题：

1. **多运行时之间怎么通信**（BusFrame 协议、Hub 路由、host 反向 RPC、事件流）
2. **终端敲一条命令到进程结束，代码怎么走**（入口 → 装配 → 路由 → 执行 → 渲染 → 退出码）

所有行号基于当前工作树（`feat/package-split-phase1` 分支，Hub 单轨化六批改动之后）。阅读时建议开着源码对照。

## 二、这套代码的 4 个核心设计思想

读代码时带着这几个问题，会更容易看懂作者的取舍：

1. **Hub 是唯一执行路径，没有兜底**
   `call_bridge` 拿不到 provider 直接报 `EXIT_RUNTIME_ERROR`（`bridge_api.rs:91`），不存在偷偷回落到 1:1 的分支。所有语言、所有命令最终都汇入同一个 `provider.call → call_sync_stream → Hub`。

2. **寻址键只有 capability 和 topic，帧里没有语言字段**
   BusFrame 里禁止出现 `language` / `runtime` / `protocolVersion` 之类的字段（协议 schema 明确禁止）。Hub 只认能力名和主题名，节点对它是完全 opaque 的 id。这是"语言无关"能成立的根本。

3. **进程内端点与子进程端点被抽象成同一个 Channel**
   `Channel` trait 只有 `send / try_recv / is_closed` 三个方法。`InProcessChannel` 用 mpsc 传对象，`StdioChannel` 用 JSON 行传字节，但 Hub 看到的是同一个 `Box<dyn Channel>`。这是能把 Rust 内置逻辑、Node、Python、Go、Dart 统一到一条总线上的关键。

4. **成本只在真正需要时付出**
   Node 和 Python 端点在构造 Hub 时就启动；Go / Dart / Rust 端点按 capability 前缀惰性 attach，且用 `BTreeSet` 保证失败也不重复尝试。所以跑一条纯 Node 命令完全不会触发 `go build`。
