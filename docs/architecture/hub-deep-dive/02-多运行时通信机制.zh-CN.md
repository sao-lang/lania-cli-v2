# 02 多运行时通信机制：BusFrame、三张表与双向 RPC

这篇讲清楚"五种运行时凭什么能互相通信"。核心答案：**它们都只说同一种语言——BusFrame 协议，并且都只通过一个中心节点——BridgeHub 转发。节点对 Hub 是完全 opaque 的 id，帧里没有任何语言字段。**

## §1 BusFrame：8 种帧构成的协议

**事实源**：`packages/products/bridge-hub/protocol/schema.json`（line 4 标注"帧协议唯一事实源，禁止在其它文件中手写帧名/字段名/错误码"）。所有语言的 `protocol/gen/<lang>/*` 都由 `gen.mjs` 从它生成。

Rust 协议 crate 只是薄壳：`lania-bridge-protocol/src/lib.rs:7` `include!("../../../protocol/gen/rust/protocol.rs");`

真正的定义在 `protocol/gen/rust/protocol.rs:33`：

```rust
33  #[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
34  #[serde(tag = "kind", rename_all = "lowercase")]
35  pub enum BusFrame {
36      Announce { #[serde(rename="endpointId")] endpoint_id: String,
40                 #[serde(default)] provides: Vec<String>,
42                 #[serde(default)] subscribes: Vec<String> },
50      Publish { topic: String, #[serde(default)] payload: Value },
55      Event   { topic: String, #[serde(default)] payload: Value, from: String },
61      Request { id: String, capability: String, #[serde(default)] params: Value },
67      Response{ id: String, result: Option<Value>, error: Option<BusErrorDetail> },
75      Bye { #[serde(rename="endpointId")] endpoint_id: String },
```

`FRAME_KINDS`（`protocol.rs:7-16`）共 8 种：核心业务帧 `announce / publish / event / request / response` + 控制帧 `subscribe / unsubscribe / bye`。编解码就是单行 JSON（`protocol.rs:96` `encode_frame` / `decode_frame` → `serde_json::to_string` / `from_str`）。

**寻址键语义**（`schema.json:7-43`，值得反复看）：

- `endpointId`：opaque 字符串，Hub 只当表键，**不做任何语言/运行时推断**。
- `capability`：点分名，如 `agent.prompt`、`host.fs.read`；`*` 结尾表示通配。
- `topic`：点分主题，`*` 结尾按前缀匹配；publish 必须是具体值（不能含 `*`）。
- `id`：correlation id，request 与 response 靠它配对。
- **不变量**：帧内禁止 `language` / `runtime` / `protocolVersion` 字段（测试 `lania-bridge-protocol/src/lib.rs:55-57` 逐字段断言）。

6 种错误码在 `protocol.rs:18-23`：`E_METHOD_NOT_FOUND / E_INVALID_PARAMS / E_INTERNAL / E_TIMEOUT / E_ENDPOINT_GONE / E_BAD_FRAME`。

## §2 Channel：抹平"进程内"与"子进程"的差异

**trait** — `lania-bridge-core/src/channel.rs:31`：

```rust
31  pub trait Channel: Send + Sync {
32      fn send(&self, frame: BusFrame) -> Result<(), ChannelError>;
35      fn try_recv(&self) -> Option<Result<BusFrame, ChannelError>>;
37      fn is_closed(&self) -> bool { false }
```

只有三个方法，且不绑定 async runtime。这是整条总线能保持同步、简单、可预测的关键。

**InProcessChannel**（进程内端点，如 Rust echo、单测）— `lania-bridge-bus/src/channel.rs:27` `pair()`：

```rust
28  let (endpoint_to_hub, hub_rx) = mpsc::channel();
29  let (hub_to_endpoint, endpoint_rx) = mpsc::channel();
31  Self::new(hub_to_endpoint, hub_rx),   // Hub 侧
32  Self::new(endpoint_to_hub, endpoint_rx), // 端点侧
```

**StdioChannel**（任意语言子进程端点）— `lania-bridge-bus/src/channel.rs:81` `new()`：

```rust
86  std::thread::spawn(move || {
87      for line in BufReader::new(stdout).lines() {
94          let item = match decode_frame(text) {
96              Err(err) => Err(ChannelError::Decode(format!("{E_BAD_FRAME}: {err}"))),
...
105         flag.store(true, Ordering::SeqCst); // EOF → closed
```

后台线程阻塞读子进程 stdout、逐行解码写入 mpsc；Hub 侧只非阻塞轮询 mpsc，pump 永不卡死。`send`（`channel.rs:115-143`）则反过来：`encode_frame` → 写一行 + `\n` + flush。

**统一接入** — `hub.rs:25` `EndpointSlot { channel: Box<dyn Channel>, ... }`，`attach()`（`:92`，进程内）和 `attach_channel()`（`:100`，任意 Channel）把两种端点塞进同一张表。`BridgeHost::attach_command()`（`lania-bridge-host/src/lib.rs:116`）负责 spawn 子进程并接上 StdioChannel。

> 这是理解"语言无关"的第二把钥匙：Hub 眼里没有"Node 端点"或"Go 端点"，只有一个个实现了 `Channel` 的槽位。

## §3 三张表与路由：Hub 的心脏

**数据结构** — `lania-bridge-bus/src/hub.rs:10-11`：

```rust
10  type CapabilityIndex = HashMap<String, Vec<String>>;   // capability → [provider id]
11  type TopicIndex = HashMap<String, BTreeSet<String>>;    // topic pattern → {subscriber id}
```

加上 `lania-bridge-core/src/pending.rs:7` `PendingTable { request_id → origin_endpoint_id }`，一共三张表，撑起全部路由。

`BridgeHub`（`hub.rs:37`）还有 `endpoints`、`endpoint_order`（确定性 pump 顺序）、`cursors`（round-robin 轮询）、`policy`。

### pump 主循环

`hub.rs:192` `pump_once()`：按 `endpoint_order` 每个通道取最多一帧 → `route_frame`；坏帧计数、断连 detach。`:233` `pump_until_idle(max_rounds)` 反复调用它。

### 帧分发

`hub.rs:241` `route_frame(from, frame)` 按 kind 分派：

```rust
248→            self.register_announce(from, provides, subscribes);   // Announce 登记
256→            BusFrame::Publish { topic, payload } => self.broadcast(from, &topic, payload),
261→                self.route_request(from, id, capability, params),  // Request 路由
263→                self.route_response(id, result, error),            // Response 回送
```

两处安全约束：`Announce.endpointId != from` 记 bad_frame（248-251）；端点回灌 `Event` 记 bad_frame（272-273，event 只能由 Hub 投递）。

### register_announce

`hub.rs:277`：先摘旧 provides/subscribes（支持重新 announce 覆盖），再写索引：

```rust
292→  for capability in &provides {
293→      self.capability_index.entry(capability.clone()).or_default().push(id.to_string());
298→  for topic in &subscribes {
299→      self.topic_index.entry(topic.clone()).or_default().insert(id.to_string());
304→  slot.provides = provides; slot.subscribes = subscribes; slot.announced = true;
```

### route_request（精确 + 通配）

`hub.rs:360`，这是能力寻址的核心：

```rust
362→      .capability_index.get(&capability).cloned().unwrap_or_default()      // ① 精确匹配
369→  let providers = if providers.is_empty() {
373→      self.capability_index.iter()
375→          .filter(|(pattern, _)| pattern.ends_with('*') && capability_matches(pattern, &capability))  // ② 通配回退
383→      if providers.is_empty() { /* 回 E_METHOD_NOT_FOUND Response */ }
397→      let provider = self.policy.select(...);                               // ③ round-robin 选一个
402→      self.pending.insert(id.clone(), from.to_string());                    // ④ 记住发起方
405→      if !self.send_to(&provider, frame) { self.pending.take(&id); }         // ⑤ 转发，失败回滚
```

### route_response 与 broadcast

`hub.rs:410` `route_response`：`pending.take(&id)` 取回发起方（取不到记 bad_frame），重建 Response 送回。

`hub.rs:332` `broadcast`：拒绝 publish topic 含 `*`；遍历 `topic_index` 找所有匹配订阅者（默认排除发布者自己），构造 `BusFrame::Event { topic, payload, from }` 投递。

匹配语义 `hub.rs:436` `topic_matches` / `capability_matches`：以 `*` 结尾按前缀匹配，否则精确相等。

> 回归测试 `hub.rs:502` `wildcard_capability_routes_host_rpc` 专门验证 `host.fs.read` 能路由到声明 `host.*` 的端点。

## §4 host 反向 RPC：Node 调用宿主的 fs/git/exec

这是整套设计里最巧妙的一处——**用同一个 capability 路由机制，实现反向调用**。

**接口** — `lania-node-bridge/src/lib.rs:27`：

```rust
27  pub trait HostRpcHandler: Send + Sync {
28      fn handle(&self, method: &str, params: serde_json::Value)
29          -> Result<(serde_json::Value, Vec<BridgeEvent>)>;
```

**Hub 侧声明** — `provider.rs:126`：attach 一个 `host-rpc` 端点，`announce_str(&["host.*"], &[])`，挂 `HostRpcHandlerBridge`（`provider.rs:57`）：

```rust
59→  fn on_request(&mut self, capability: &str, params: Value, ...) -> Result<RouteOutcome> {
        // 把 "host.fs.read" 原样转给 handler，错误包成 E_INTERNAL
```

**宿主实现** — `lania-host/src/runtime/host_rpc.rs:447` `HostRpcAdapter::handle` → `:220` `dispatch_host_rpc()` 按前缀分发：`host.exec.*` → exec、`host.git.*` → git、`host.fs.*` → fs，还有 pm/runtime/log/tasks/progress/interaction。

**Node 侧发起** — `bridge-runtime/ts/src/entry/hub-stdio.ts:116-156`：把 hostCall 的写出重定向成 `runtime.request(method, params)`，外层加 30s `Promise.race` 超时：

```ts
132→  const result = await Promise.race([ runtime.request(method, params), ... ]);
142→  handleHostResponse({ id, result });
```

**完整闭环**（记住这条链，面试/讲架构很有用）：

```
Node hostCall(host.fs.read)
  → runtime.request 发 BusFrame Request(capability="host.fs.read")
  → Hub route_request 精确未命中 → host.* 通配命中 host-rpc 端点
  → HostRpcHandlerBridge.on_request → HostRpcAdapter.handle → dispatch_host_rpc → fs
  → Endpoint.respond 写 BusFrame Response
  → Hub route_response 按 pending 找到 node-hub
  → StdioChannel 写回 Node stdin → Node EndpointRuntime.handle 收 response
  → handleHostResponse resolve promise → hostCall 返回
```

1:1 模式（非 Hub）走的是 envelope（`lania-node-bridge/src/client/process.rs:262-333`），但复用同一个 `HostRpcHandler`，语义一致。

## §5 事件流与"逐 token 实时"

**事件生产** — `bridge-runtime/ts/src/entry/hub-stdio.ts:66` `makeHubHooks()`：插件 emit 的事件在回调里立即 `publish(event)`（81-83 行）；生成的 `runtime.ts:39` `publish()` 写出 BusFrame publish 帧（`write()` 在 `:51` 写 `encodeFrame(frame)+"\n"`）。

**Hub 广播** — `broadcast()`（§3）转成 event 帧；宿主端点构造时订阅 `event.*`（`provider.rs:117`）。

**event → 渲染** — `provider.rs:201` `call_sync_stream()` 在 pump 循环里边收边回调：

```rust
240→  BusFrame::Event { topic, payload, .. } => {
241→      on_event(BridgeProviderEvent::new(topic, payload));
242→  }
```

`lania-host-core/src/lib.rs:27` 定义 `BridgeProviderEvent { method, params }`；`:84` `call_stream` 默认实现是先收集再回放，**Hub provider 覆盖了它**。

**为什么能逐 token 实时**（`commands/pi/rust/src/bridge.rs:46` `prompt()`）：

```rust
55→  let result = self.provider.call_stream(&method, params, &mut |event| {
56→      if let Some(parsed) = AgentEvent::from_method(&event.method, &event.params) {
57→          on_event(parsed);
58→      }
59→  }).await?;
```

`call_sync_stream` 不等 response 才回放事件，而是每轮 pump 里刚收到 Event 帧就立即回调，回调穿透到 `AgentEvent::from_method`（`lania-agent-core/src/event.rs:140`，`event.agent_text_delta → TextDelta`）直接渲染。测试 `provider.rs:499` `call_stream_delivers_events_via_callback` 验证真实 Node 端点的 `event.log` 在回调中实时到达。

长任务（response 先返回、事件后到）则用 `drain_events()`（`provider.rs:343`）在等待期间持续泵事件。

## §6 五种语言说的是同一份协议

所有语言复用 `schema.json` 生成的协议骨架，但"把业务的 emit 转成 Hub publish"各有实现（详细对比见 [03](./03-多语言接入与惰性attach.zh-CN.md)）。这里只列写出帧的关键函数，方便对照：

| 语言   | 写帧函数                  | 位置                                           |
| ------ | ------------------------- | ---------------------------------------------- |
| Node   | `write(frame)`            | `protocol/gen/ts/runtime.ts:51`                |
| Python | `EndpointRuntime.write()` | `protocol/gen/py/lania_bridge_runtime.py:35`   |
| Go     | `EndpointRuntime.Write()` | `protocol/gen/go/runtime.go:52`                |

业务脚本手写帧的：Go `writeFrame()`（`lan_go_bridge.go:244`）、Dart `_writeFrame()`（`lan_dart_bridge.dart:108`）、Rust `write_frame()`（同上）。

## 一句话总结

Bridge Hub 的通信机制可以浓缩成：**一份语言无关的帧协议（BusFrame）+ 一个统一的通道抽象（Channel）+ 三张索引表（capability_index / topic_index / pending）**。请求按 capability 精确或通配路由，响应按 pending 回送，事件按 topic 广播；host 反向 RPC 复用了同一套路由，只是把 capability 换成了 `host.*`。五种运行时说同一种协议、走同一条总线，彼此之间没有任何直连。
