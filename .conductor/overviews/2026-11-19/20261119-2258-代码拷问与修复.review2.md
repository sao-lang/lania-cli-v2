## 本轮新发现

### [Should] webpack build 编译错误（`stats.errors` 非空）仍被判成功

- **文件:行号**：`packages/foundation/bridge-slices/compiler/ts/src/plugins/compiler-adapters/webpack.ts:272, 292-308, 329-339`；消费侧 `packages/commands/workspace/rust/src/build.rs:28-38`。
- **现象**：`compiler.run/watch` 回调在 `error` 为 null、`stats` 正常返回但 `stats.toJson().errors` 非空（真实的编译错误，如 TS 类型错误、模块解析失败）时**不会抛异常**，因此不走 catch。代码仅把错误写成 `compilerIssueEvent`（:292-296）和 `compilerDoneEvent(..., errors.length === 0, ...)`（:302-308，事件里 success=false）；但返回的 result（:329-339）仍是 `createCompilerResult('webpack','build','runtime', {...})`，**无 `success` 字段**。
- **后果**：Rust `resolve_build_exit_code` 只读 `result.success`，缺失即 `unwrap_or(true)`（build.rs:29-32）→ `EXIT_SUCCESS`。`event.compiler_done` 的 success 只驱动进度条 UI（events.rs:213-221），不影响退出码。于是 webpack 真实编译失败时 CLI 退出码为 0、被判“构建成功”，与 README 契约及“失败不再伪造成功”目标直接冲突。这是 catch 分支修完后仍存在的“web 失败被判成功”残留，且 webpack 编译错误通常不抛异常，属高频主路径而非边角。
- **改法**：在 `errors.length > 0` 时给 result 补 `success:false` 与 `error`（可复用 `failureExecution('webpack','build', ...)`，或把 :329 的 result 与 `success: errors.length === 0` 合并）；并补一条插件级测试：注入 `compiler.run` 回调返回 `stats.toJson()` 含 `errors:[{message:'boom'}]`，断言 `result.success === false`。注意保持既有 `webpack adapter handles build runtime flow` 测试（errors 为空时）不被破坏。

### [Nit] rollup dev 在 watch 报错或 1500ms 超时未收到 END 时仍报成功

- **文件:行号**：`packages/foundation/bridge-slices/compiler/ts/src/plugins/compiler-adapters/rollup.ts:84-121, 102-110, 144-148, 153-160`。
- **现象**：`firstBuildEvents` 用 1500ms 超时 `resolve`（:117-120），`ERROR` 事件只被收集为 `compilerIssueEvent`（:102-110），`doneEvent` 硬编码 `success=true`（:144），result 无 `success` 字段（:153-160）。watch 从未发 END（配置卡死/启动失败）或首轮构建 ERROR 时，仍返回成功语义。
- **后果**：极端情况下 rollup watch 未真正就绪却被判成功；“失败不再伪造成功”在 dev/watch 分支仍有边角残留。
- **改法**：若 `firstBuildEvents` 观察到 ERROR 或超时未收到 END，则对 result 补 `success:false`；或至少把 doneEvent 的 success 与是否观察到 ERROR 绑定。（dev 为长任务，优先级低于 build 的 Should。）

### [Nit] 新测试未断言错误来源，无法区分 adapter catch 与 worker 层兜底

- **文件:行号**：`packages/foundation/bridge-slices/compiler/ts/src/plugins/compiler.test.ts:275-311`；对照 `compiler.ts:75-79`。
- **现象**：测试仅断言 `success===false` 与无伪造事件。若 vite adapter 的 catch 被回滚成“抛到 worker 外层”，`runCompilerInWorker(...).catch(() => undefined)`（compiler.ts:70）+ `failureExecution('runtime adapter unavailable')`（:79）同样产出 `success:false` 且无伪造事件，测试仍会通过。
- **后果**：测试锁定的是端到端结果，不能保证覆盖的是 `vite.ts:182` 这一行；若有人把 catch 删掉让错误上抛，测试不会报警。
- **改法**：补一条 `compiler_issue`/`result.error` 断言含 `vite boom` 来源串，把断言钉在 vite adapter 自身的 catch 产物上（worker 兜底文案为 `runtime adapter unavailable`，可区分）。
