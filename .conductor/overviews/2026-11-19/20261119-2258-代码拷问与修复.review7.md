## 5. 分级问题清单

### Should

- **S1 — `store.rs:1082-1083`、`1116-1122`（panic 时环境/资源不清理）**
  - **后果**：清理逻辑写在函数尾部顺序执行。任一断言（`1097`、`1111`）或 `.expect()`（`1095`、`1109`）panic 时，`RUNEX_NODE_MIRROR` 不会恢复、`shutdown.send` 不发、临时目录不删。当前 crate 内无其它测试读该变量，故**不会立即引发级联失败**；但 RED 验证或未来任何读取该变量的测试会在同一进程看到指向已死 server 的镜像地址而失败，并泄漏 server 线程与临时目录。回归测试失败时污染环境，违背测试隔离原则；`store.rs:990` 注释"设置/恢复"也仅在成功路径成立。
  - **改法**：用 RAII 守卫（struct + `Drop`）保存 `previous_mirror` 与 `shutdown` sender，在 `Drop` 中恢复环境变量、发送 shutdown、删临时目录；测试体只持有守卫，panic 自动展开时即清理。这样也不再依赖"恰好无人读变量"的隐式前提。

### Nit

- **N1 — `store.rs:1029-1031`、`1121`（server 关闭信号不可靠 / 线程泄漏）**
  - **后果**：server 线程阻塞在 `listener.incoming()` 的 accept，`shutdown.send(())` 后需等下一个连接才执行 `try_recv`；无后续连接时线程不退出。单次运行泄漏 1 线程，panic 路径连 send 都没有。
  - **改法**：`listener.set_nonblocking(true)` 配合轮询退出，或 shutdown 时由主线程自连接唤醒 accept；更省事的是在 S1 的 RAII 守卫里统一处理关闭与回收。

- **N2 — `store.rs:1037-1040`（HTTP 请求行单次 `read` 解析）**
  - **后果**：只 `read` 一次并取首行作为 path，隐式依赖 loopback 短 GET 的首包即含完整请求行。若 ureq 分包发送导致首行被截断，路由落到空 body 分支，产生"假失败"（不是假绿），增加偶发 flake 风险。概率很低。
  - **改法**：循环读到 `\r\n\r\n` 或至少读到首个换行再解析；或引入轻量 HTTP server 作 dev-dependency 替代手写 server。
