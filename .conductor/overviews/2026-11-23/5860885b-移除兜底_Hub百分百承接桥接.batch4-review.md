## 1. 协议正确性（BusFrame 编解码）

事实源：`protocol/schema.json`、`protocol/gen/{py,go,dart,rust}/...`、`rust/lania-bridge-bus/src/hub.rs`。

| 帧       | 必需字段                               | Python                                             | Go                           | Dart                             |
| -------- | -------------------------------------- | -------------------------------------------------- | ---------------------------- | -------------------------------- |
| announce | kind, endpointId, provides, subscribes | `runtime.boot` → `announce_frame`（gen/py:36-42）✓ | `lan_go_bridge.go:880-883` ✓ | `lan_dart_bridge.dart:798-803` ✓ |
| publish  | kind, topic, payload                   | `_hub_emit:44` ✓                                   | `emit:271` ✓                 | `_emit:90-94` ✓                  |
| request  | kind, id, capability, params           | 由 Rust `Endpoint` 发帧 ✓                          | 读帧 `903-905` ✓             | 读帧 `825-829` ✓                 |
| response | kind, id, result?, error?              | `runtime._serve:86` ✓                              | `932-935` ✓                  | `847-852` ✓                      |
| event    | topic, payload, from                   | Host 订阅 `event.*`（provider.rs:116）✓            | —                            | —                                |

**结论**：三语言 BusFrame 顶层字段名全部与 schema 一致，`endpointId` 与 `attach_command` 的 id 一致（hub.rs:248 的来源校验不会被坏帧丢弃）。GO/Dart 的 `error` 对象含 `data:null`，Rust `BusErrorDetail.data: Option<Value>` 可解码，无问题。

- **N1（Nit）**：三个手写业务脚本仍含 `requestId` / `bufio.NewScanner` / `stdin` / `LineSplitter` 等 `schema.json:18-29` 的 `forbiddenSkeletonKeywords`。这些词只出现在 1:1 envelope 内部且被 `hubMode` 分支丢弃，不进入 BusFrame 顶层；仓库也未发现对该清单的自动校验测试，故不构成 Blocker，但属“协议知识写两遍”的设计偏离，后续应把 1:1 分支彻底删除。

## 2. Python monkey-patch（`endpoint.py`）

- **覆盖性 ✓**：`biz.emit = _hub_emit`（endpoint.py:51）覆盖了完整事件链 `emit_diag(lan_py_bridge.py:122) → emit_event(:98) → emit(:92)`。
- **无 stdout 污染 ✓**：`handle_lint`(:501-551)/`handle_build`(:554-579) 不直接写 stdout；`worker()` 里的 `sys.stdout.write`(:695/712/728) 运行在 `--worker` 独立子进程（:735-736），不经过 Hub 端点的 stdout。
- **response envelope 忽略正确 ✓**：`_hub_emit` 只处理 `type=="event"`（endpoint.py:37-38），response 被丢弃；结果由 `Hooks.on_request` 返回值承载，经 `runtime._serve` 组装 BusFrame response（gen/py:79-88）。
- **capability 分派 ✓**：`lint.*` → `biz.handle_lint`，`build.python` → `biz.handle_build`，内建 `bridge.*` 就地处理（endpoint.py:58-80）。

- **N2（Nit）**：`_hub_emit:45` 只捕获 `RuntimeError`；若 `publish` 抛出其它异常会冒泡到 `Hooks` 的宽 except，被误报为 `E_LINT_FAILED`。概率极低。

## 3. Go `serveHub`（手写分发）

- **语义一致性基本 ✓**：`bridgeMethods`（:49-56）全部覆盖 —— `bridge.ping/heartbeat/shutdown`、`lint.go-vet`/`lint.golangci-lint`（`strings.HasPrefix("lint.")`）、`build.go`（:911-931）。
- **result 组装 ✓**：`emitResponse` 在 hubMode 下被 `emit:258-262` 忽略；`serveHub` 直接构造 BusFrame response（:932-936），`lintResult` 结构体经 `json.Marshal` 正常序列化。
- **`decodeParamsFromAny` ✓**（:947-952）：`json.Marshal → decodeParams` 二次转换，与 1:1 `decodeParams(json.RawMessage)` 语义一致。
- **事件顺序 ✓**：`emitDiag → emitEvent → emit → writeFrame(writeMu)` 串行，lint_start → diag → lint_result → response 顺序有保证。

- **S1（Should，中）**：`serveHub` 的 `bridge.shutdown` 分支（:915-916）**没有** `emitEvent("event.shutdown", ...)`，而 1:1 `handleRequest`（:788-790）和 Python Hooks（endpoint.py:63）都会发。同一 capability 在两种模式下事件语义不一致，订阅者（含 host）收不到 shutdown 事件。建议补一行 publish。

## 4. Dart `_serveHub`

- **`_hubMode` 初始化时机 ✓**：top-level `final`（:74）在 Dart 中惰性初始化，父进程 spawn 前已设置 env，不会读到未初始化值。
- **队列顺序 ✓**：`_writeFrame`(:108-118) 与 `_emit`(:96-104) 共用 `_outbox` FIFO；announce → diag/publish → response 顺序确定；`main` 退出前 `await _outbox`(:868) 保证不丢尾帧。

- **S2（Should，高）**：`_serveHub` 的 lint/build 分支（:838-843）**缺少 try/catch**。而 1:1 `_handleRequest`（:680-699/:702-711）明确用 `try/catch` 防止“bridge 因单个工具崩掉”。Hub 模式下 `_handleLint`/`_handleBuild` 抛异常会穿透 `_serve → main`，进程直接退出，Hub 的 pending 请求挂到 30s 超时后上层回落 CLI spawn。这是可用性回归，应补与 1:1 等价的错误封装（`E_LINT_FAILED`/`E_BUILD_FAILED` → BusFrame response.error）。
- **S3（Should，中）**：`bridge.shutdown` 分支（:836-837）同样未 publish `event.shutdown`，与自身 1:1 路径（:665-668）及 Python 不一致。
- **N3（Nit）**：`_serveHub` 的 lint 分支未发 `event.lint_start`/`event.lint_result`（自身 1:1 也不发，与 Go 不一致）；属既有跨 bridge 差异，非本批引入。

## 5. 惰性 attach（`provider.rs:255-280`）

- **capability 前缀覆盖 ✓**：Go `lint.go-*` / `lint.golangci*` / `build.go`，Dart `lint.dart-*` / `build.dart`，与 `lint.rs:35-39` 实际方法名（`lint.go-vet`/`lint.golangci-lint`/`lint.dart-analyze`）及 build 方法名完全匹配；任务点名的 5 个方法全覆盖。
- **announce deadline 逻辑 ✓**：`is_announced(id)` + 30s + pump/sleep 循环（:275-279），不会被其它端点（如 host.\*）提前满足，正确。

- **S4（Should，高）**：`attach_dart`（`lib.rs:176-187`）**硬编码 `Command::new("dart")`**，绕过了 `lania_dart_bridge::resolve_dart`（`lania-dart-bridge/src/lib.rs:73-92`）的 FVM / `LANIA_DART` / `dart.bat→dart.exe` 处理。Windows Flutter 项目里 PATH 上常是 `dart.bat`（CreateProcess 无法直接拉起），会 attach 失败；叠加 S5 的“失败不重试”，Dart 能力在该类环境永久不可用。应改用 `resolve_dart` 的解析结果。
- **S5（Should，中）**：`attached_languages` 在 attach **之前**插式标记（:270），失败（含瞬时 spawn/编译失败）永不重试。“避免反复编译”的初衷可理解，但把“编译失败”和“临时环境问题”一棍子打死；建议区分：编译/二进制缺失可标记，spawn 失败允许有限重试。
- **S6（Should，高）**：`call_sync` 持有 `MutexGuard` 时调 `ensure_language_endpoint → attach_go → ensure_binary()`（`lib.rs:166`，首次编译数十秒）。期间所有并发 `call_sync`/`drain_events`/`shutdown` 全被阻塞，且在 tokio 线程上同步等待有饿死风险。建议把 `ensure_binary()` 的编译阶段移出锁（或用 `OnceLock` + 双检锁），仅在持锁期做 spawn。
- **S7（Should，中）**：`CALL_TIMEOUT` 固定 30s（:50），忽略宿主 `policy.timeout_ms` 配置；且 `ensure_binary` + announce 等待（最长约 60s）不计入调用超时，总时长不可控。
- **N4（Nit）**：`lint.rs:216`/`build.rs:121` 在调用 Hub 前先 `ctx.bridge(kind)`，其 `client_for → resolver` 已触发一次 `ensure_binary`（`bridges.rs:214-216`），削弱了 provider.rs:164-165 “惰性编译只在需要时付出”的收益（有缓存，不重复编译）。

## 6. `call_runtime_bridge` 走 Hub（`bridge_api.rs:236-301`）

- **`_client` 保留安全 ✓**：仅用于调用方构造 `BridgeRequest`，不参与执行；调用方 lint.rs:224/build.rs:125 仍用 `client.request(...)` 生成请求对象。
- **退出码语义 ✓**：lint.rs:250 从 `payload["exitCode"]` 取；build.rs:140 用 `resolve_build_exit_code(result)`；均基于 `exchange.response.result`，未被 Hub 化破坏。
- **error 恒 None 可接受 ✓**：协议级 error 已在 `call_sync:236-238` 转 `Err`，业务错误在 result 内部（如 build 的 `success:false`），`response.error` 恒 None 不丢信息。

- **S8（Should，高）**：**事件不再被渲染**。旧实现 `call.collect_until_response(|event| self.apply_bridge_event(...))`（diff 删除段）会逐条渲染 `event.diag`/进度；新实现只把 `provider_exchange.events` 转成 `BridgeEvent` 塞进 `exchange.events`（:279-299），而 `call_runtime_bridge` 自身**不调用** `apply_bridge_events`，lint.rs:232-245 / build.rs:137-144 也没有调用。`event.diag` 的工具日志、`event.lint_start/result` 的进度在 lint/build 路径上被静默丢弃，与 `call_bridge:158` 的处理不一致。建议在 `call_runtime_bridge` 构造 exchange 后调用 `self.apply_bridge_events(&request, &exchange)`（或让调用方调用），恢复渲染链。

## 7. 跨语言 method 冲突

- **bridge.ping / bridge.heartbeat**：Node/Python/Go/Dart 四方都 announce；Hub `ProviderPolicy::RoundRobin`（`policy.rs:1-22`, `hub.rs:397-400`）按 capability 轮询，四个实现都返回 ok —— **无害**。
- **bridge.shutdown**：四方都 announce，轮询只会通知其中一个端点。当前生产长任务停止走 `compiler.stop`（`long_running.rs:113`，仅 Node 声明），**主路径风险被规避**；但 `bridge.shutdown` 若被外部/未来代码调用，语义不完整（只停一个子进程）。叠加 S1/S3 的事件缺失，shutdown 观测会不一致。**Should（中）**：建议把 `bridge.shutdown` 改为广播语义，或从非 Node 端点的 `provides` 中移除。
- **echo 占位端点不冲突 ✓**：`register_language` 注册 4 个 echo 端点（`PROVIDES=["echo.ping","echo.upper"]`），不与 bridge._/lint._ 重叠。

## 8. 整体：能否宣称“所有运行时都经 Hub 桥接”？

**不能。** 核心 lint/build 执行已单轨，但存在以下 Hub 之外的桥接路径：

- **S9（Should，高，宣称级）**：`resolve_runtime_command → toolchain_command`（`bridge_api.rs:372-400`）仍直接 `self.node_bridge()` + `client.call_async("toolchain.describe", ...)`，这是 1:1 NodeBridgeClient 调用。每个非 JS 项目的 `lan build` 都会走它。字面意义上“所有桥接经 Hub”不成立。
- **S10（Should，高，宣称级）**：Rust bridge 仍以 `__lania_rs_bridge` 独立 stdio 1:1 协议运行（`bridge_setup.rs:25-30`），没有作为 Hub 端点 attach；Rust 的 lint/build 不经过 Hub。
- **应明确**：`lint.rs:238-244` / `build.rs:145-154` 在 bridge 失败时仍回落 Rust CLI spawn；`bridge_api.rs:91-125` 对 `call_bridge` 已硬要求 provider，但 `call_runtime_bridge` 的调用方仍保留回落。这与“移除兜底”的命名不矛盾（回落是 §5.3 的 CLI 兜底而非 1:1 bridge 兜底），但对外表述需精确。

**达成度结论**：

- 本批声明范围（Python/Go/Dart 三种语言的真实 lint/build bridge 接入 Hub 单轨）—— **达成**。
- 全项目“100% Hub 承接桥接”宣称 —— **未达成**（S9/S10 是硬缺口；在修掉之前建议使用“lint/build 执行路径已单轨 Hub”这类精确表述）。

## 附：分级清单

### Blocker

无（0）。未发现会让本批核心链路整体失效的静态问题；手动端到端基线与本审查一致。

### Should（应修）

1. **S1** Go `serveHub` 的 shutdown 未 publish `event.shutdown`（`lan_go_bridge.go:915`）。
2. **S2** Dart `_serveHub` 的 lint/build 无 try/catch，异常会杀进程（`lan_dart_bridge.dart:838-843`）。
3. **S3** Dart shutdown 未 publish `event.shutdown`（`lan_dart_bridge.dart:836`）。
4. **S4** `attach_dart` 硬编码 `"dart"`，绕过 FVM/LANIA_DART/dart.bat 解析（`lib.rs:176-187`）。
5. **S5** `attached_languages` 失败不重试过于绝对（`provider.rs:266-272`）。
6. **S6** 持 Mutex 调 `ensure_binary` 阻塞全局调用（`provider.rs:198/271`, `lib.rs:166`）。
7. **S7** `CALL_TIMEOUT` 忽略 `policy.timeout_ms`，且不计 attach 等待（`provider.rs:50,205`）。
8. **S8** `call_runtime_bridge` 收集但不渲染 events，lint/build 日志/进度丢失（`bridge_api.rs:279-299`）。
9. **S9/S10** toolchain.describe 与 Rust bridge 仍在 Hub 之外，“100%”宣称不成立（`bridge_api.rs:372`, `bridge_setup.rs:25`）。

### Nit（建议）

- **N1** 手写脚本残留 schema 禁用词（仅 1:1 分支，不入 BusFrame）。
- **N2** Python `_hub_emit` 只 catch `RuntimeError`。
- **N3** Dart lint 未发 lint_start/lint_result（既有差异）。
- **N4** `ctx.bridge(kind)` 提前触发 `ensure_binary`，削弱惰性收益。
- **N5** 内建错误码 `E_UNSUPPORTED` 非 schema 枚举（E_METHOD_NOT_FOUND 等），Hub 透传无碍但属手写错误码。
