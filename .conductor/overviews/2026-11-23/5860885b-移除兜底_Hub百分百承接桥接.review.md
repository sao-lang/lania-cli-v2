# 独立红队评审 / 5860885b / 第 1 批：扩展 BridgeProvider 接口承载事件流

- 评审视角：独立评审员，未参与改动，假设改动有错、主动找反例。
- 依据：spec / contract + 工作树三文件 diff + 周边实现（Hub 路由、node-bridge 协议、回落与长任务链）。
- 验证基线采纳用户所述（cargo check rc=0、单包测试全绿、protocol 检查 rc=0）。绿灯本身不构成正确性证据，下面逐条给出可证伪的反例。

## 一、七维评审小结

| 维度     | 结论                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------- |
| 正确性   | 接口签名扩展自洽、编译通过；但**事件收集路径在当前 Hub 配置下不可达**（见 B1），核心目标落空。                         |
| 错误处理 | provider 业务错误经 `anyhow::bail!` → `_ => None` 静默回落，不上报（S5）；未知事件 method 仅 Warn 丢弃（S3）。         |
| 并发     | Mutex 覆盖同步 pump + `thread::sleep`，async 中不 yield，`tokio::time::timeout` 对其失效（S1/S2）。                    |
| 资源     | 200 轮固定 pump + 1ms sleep，无 deadline；持锁占 tokio worker（S2）。                                                  |
| 性能     | 同步阻塞 + 串行 Mutex；单进程单命令场景下影响有限，但语义上不可超时取消。                                              |
| 安全     | 无新增注入面：`method` 仅作枚举键匹配，`params` 为 Value 透传；无发现。                                                |
| 可维护性 | `method` 用 String 解耦合理，但把事件名校验推给下游、靠魔法字符串（S3/N1）；三处“保证不退化”注释与实际能力不符（S4）。 |

## 二、接线四问

1. **谁调用它**：`call_bridge`（bridge_api.rs:98）在 before-hook 改写 params 后调用 `provider.call`；测试里 Stub 与 `call_sync` 亦调用。✓
2. **它调用谁**：`HubBridgeProvider::call` → `call_sync` → `host.pump_until_idle` / `endpoint.serve_until_idle` / `client.try_recv`（provider.rs:84-132）。✓
3. **信号被谁消费**：Hub 侧 Event 帧本应被 `client.try_recv` 收集 → `BridgeProviderEvent` → `BridgeEvent` → `apply_bridge_events` 渲染。**但 client 未订阅 topic，链路在第一跳即断**（B1）。
4. **数据流闭环吗**：Response 闭环（request→pending→response 回 host）✓；Event 链路 **不闭环**（无订阅者，broadcast 投递数为 0），且 response 之后的运行期事件无 `active` 句柄承接（S4）。

## 三、问题清单

### Blocker

**B1 — 事件收集代码不可达：host 端点从未订阅 topic，`client.try_recv()` 收不到任何 `BusFrame::Event`**

- 位置：`provider.rs:58`（`let client = host.attach("host")`）、`provider.rs:102-118`（drain + Event 分支）、`provider.rs:159`（语言端点 `announce_str(PROVIDES, &[])`）；对照 `hub.rs:100-115`（`attach_channel` 初始化 `subscribes` 为空）、`hub.rs:311-337`（`broadcast` 只投递给 `topic_index` 中的订阅者）。
- 证据链：
  1. `BridgeHost::attach` 只做 `hub.attach(id)`（`lib.rs:103-105`），不 announce、不 subscribe；`client` 创建后无任何 `subscribe`/`announce` 调用。
  2. Hub `broadcast`（hub.rs:311-337）仅把 Event 发给匹配 topic 的 `subscribers`；`host` 不在任何 topic 的订阅集合里。
  3. 语言端点 `register_language` 用 `announce_str(PROVIDES, &[])`（provider.rs:159），`subscribes` 也为空；`EchoHandler` 的 `on_event` 是空实现、`on_request` 不 publish（`adaptors/rust/endpoint.rs:16-40`）。当前 Hub 内**没有任何端点订阅任何 topic**。
  4. 每个端点独立 channel，`client.try_recv()` 只能读到 Hub `send_to("host", …)` 的帧；而 `send_to` 的 Event 来源只有 `broadcast`。因此 `provider.rs:114-116` 的 Event 收集分支**永不进入**，`events` 恒为空。
- 后果：改动声称“端点事件连同响应带回、保证进度/日志不退化”，实际 `BridgeProviderExchange.events` 永远为空。这不是“已知后续范围”的中性限制——当前代码主动编码并注释了事件收集，制造了“已接通”的假象，却在源/订阅两侧都断开；后续批次即使让语言端点 publish 事件，host 仍收不到。与 spec AC-6（无 fake/占位）和“反兜底、真承接”目标直接冲突。
- 反例（可复现）：注册一个会 `publish("event.progress", …)` 的端点并 `call_sync`，断言 `exchange.events.len() > 0` 必然失败；现有测试 `declared_capability_is_routable_after_language_registration`（provider.rs:219 `assert!(exchange.events.is_empty())`）恰好因为无 publish/无订阅而“通过”，无法验证事件路径。
- 改法：在 `new()` 中让 `client` 订阅事件 topic（如 `client.announce_str(&[], SUBSCRIBES)` 或按 FR-2 规范订阅 `event.*`），确保 publish 的 Event 被广播到 host 端点；或改为在 Hub 侧按 request 聚合 Event 后随 Response 一并回送，不依赖 `client.try_recv()` 的隐式订阅。并补一条“端点 publish → `call_sync` 返回 events 非空且有序”的测试，否则 AC-4/AC-5 无从成立。
- 边界说明：事件“源”（语言端点真实 publish）属后续批次（FR-3/FR-7），但 host 侧连订阅都未做，是本批引入的确定性缺口，不修则后续批次无法闭环。

### Should

**S1 — `tokio::time::timeout` 对 provider 分支形同虚设**

- 位置：`bridge_api.rs:96-100`（`timeout(..., provider.call(...))`）、`provider.rs:137-144`（`call()` 内直接同步调用 `call_sync`）。
- 后果：`call_sync` 是同步阻塞函数（内部 `pump_until_idle`、`serve_until_idle`、`std::thread::sleep`），在 `async_trait` 生成的 future 中一次性同步跑完、不 yield。外层 `timeout` 永远没有机会在中间打断；provider 卡住时无法按 `policy.timeout_ms` 超时，且会阻塞 tokio worker（current_thread runtime 下阻塞整个 executor）。第 1 批保留回落，故表现为“迟迟不回落”而非报错。
- 改法：用 `tokio::task::spawn_blocking` 包裹 `call_sync`（注意 Mutex 与 `Send` 约束），或把等待改为 async 轮询 + `tokio::time::sleep`，让 timeout 可真正取消；或在 future 内显式检查 deadline。

**S2 — 200 轮固定 pump + sleep，超时不确定且全程持锁**

- 位置：`provider.rs:84-86`（MutexGuard 覆盖整个循环）、`provider.rs:91,94,97,100,129`（`0..200`、`pump_until_idle(50)`、`serve_until_idle(16)`、`sleep(1ms)`）、`provider.rs:131`（`E_TIMEOUT`）。
- 后果：超时时长随 pump 负载漂移（200×1ms 基线 + pump 开销），无统一 deadline；长循环持 `Mutex`，与 `register_language`（provider.rs:147）串行，并发调用全部排队。
- 改法：用 `Instant::now() + timeout` 的 deadline 循环替代固定轮数；缩小持锁临界区（pump/serve 可在锁内，但避免 sleep 持锁）；记录实际耗时用于诊断。

**S3 — 非法/未知事件 method 被丢弃，可观测性不足且无编译期校验**

- 位置：`bridge_api.rs:108-124`（`filter_map` + `serde_json::from_value::<BridgeEvent>` + Warn 日志）、`host-core/lib.rs:28-31`（`BridgeProviderEvent.method: String`）。
- 评估：`from_value` 本身可靠——`BridgeEvent` 无 rename_all，构造的 `{"method","params"}` 字段名匹配；`BridgeEventMethod` 各变体有显式 `rename = "event.*"`（`protocol.rs:70-134`），规范 topic 名（如 `event.progress`）能正确解析，Vec 顺序在收集/转换/消费三段均保持。
- 后果：任何不在枚举内的 method（新增事件、端点自定义 topic、拼写差异）解析失败即被丢弃；虽有 `LogLevel::Warn` 日志（bridge_api.rs:115-120），但可能被日志级别过滤，且无计数/指标，静默降级风险仍在。`String` 把事件名合法性完全推给下游，host-core 无法校验。
- 改法：在 host-core 定义权威事件 method 常量或做枚举化校验，避免散落魔法字符串；把丢弃事件计入 diagnostics/指标（而非仅日志），保证可观测。

**S4 — 长任务运行期事件仍丢失，`active=None` 未解决 FR-7，注释误导**

- 位置：`bridge_api.rs:138`（`active: None`）、`bridge_api.rs:199-207`（`maybe_wait_for_shutdown`）、`long_running.rs:44-61`（`active` 为 None 时只 `cancellation.cancelled().await`，不消费事件）、`provider.rs:120-128`（收到 Response 即 return，response 之后产生的事件不再收集）。
- 后果：dev/watch 的 response 通常在启动完成时返回，之后的 `watch_change`/diag/日志在 provider 链路无句柄消费，仍然丢失。相比改动前（events 恒空）不算新增退化，但 bridge_api.rs:103-104 与 provider.rs:88-89 的“保证进度/日志不退化”注释对长任务不成立。
- 改法：明确文档“第 1 批仅覆盖 response 之前事件”；FR-7 落地时让 `BridgeProviderExchange` 带回长任务句柄/事件订阅，使 `active` 非空并在 `maybe_wait_for_shutdown` 中持续消费。

**S5 — provider 业务错误被静默回落，不上报**

- 位置：`provider.rs:121-123`（错误时 `anyhow::bail!("{code}: {message}")`）、`bridge_api.rs:141`（`_ => None`）、`bridge_api.rs:149`（回落 `dispatch_bridge_request`）。
- 后果：Hub 返回的 `E_METHOD_NOT_FOUND`/`E_TIMEOUT`/`E_INVALID_PARAMS` 被转成 `Err` 后走回落分支，由 1:1 链路掩盖，用户看不到 provider 的真实失败原因；与“移除兜底 + 明确错误语义”（contract Invariants）方向相反。第 2 批删回落时才会暴露为真正问题。
- 改法：删回落批次同步把 provider 的 `Err`/exchange 错误直接映射为 `ExecutionError`（保留 code/exit code）；第 1 批至少将回落原因写入日志/Warn，避免静默。

### Nit

**N1 — `BridgeProviderEvent.method` 为裸 String，测试与调用点手写魔法字符串**

- 位置：`host-core/lib.rs:28-31,162-163`（`"event.progress"` / `"event.log"` 字面量）；`bridge_api.rs:110`（`event.method` 直传）。
- 后果：事件名无单一权威来源，新增/改名易遗漏校验（呼应 S3）。
- 改法：提供事件 method 常量模块或 `From<&str>` 校验入口；测试改用常量。

**N2 — try_recv drain 去掉 `break` 后缺少“为何不 break”的说明**

- 位置：`provider.rs:101-119`（`outcome` 只记录匹配 id 的 Response，循环继续 drain 以收集同批 Event）。
- 后果：语义正确（同批事件在 response 前收集），但后人易把“去掉 break”改回而引入事件遗漏。
- 改法：补一行注释说明需 drain 完整批次以收集 response 前后到达的事件，并说明跨批次的事件不在本批范围。

**N3 — 手工构造的 `BridgeResponse.error` 恒为 None，缺少说明**

- 位置：`bridge_api.rs:127-134`（`error: None`）。
- 后果：读者可能误以为 provider 的协议错误会通过该字段上抛；实际错误走 `Err` 通道（见 S5）。
- 改法：加注释或断言说明 provider 命中路径 error 恒 None、错误由 `anyhow::Result` 承载。

---

## 四、结论

- **重复消费**：未发现。provider 分支仅在 `bridge_api.rs:135` apply 一次；回落分支由 `dispatch_bridge_request` 内部 apply 一次（requests.rs:74 / 164）；两者在 `match provider_dispatch` 中互斥（Some/None），调用方不对 exchange.events 二次渲染（回落分支长期如此，未暴露重复）。✓
- **遗漏**：存在，且为根因级（B1：事件根本到不了收集点；S4：response 后事件无句柄）。
- **顺序**：收集（FIFO push）→ 转换（filter_map 保序）→ 消费（按 Vec 遍历）全程保序，且 events 在 response 错误上抛前渲染，符合契约 invariant。✓
- **依赖方向**：新类型仅依赖 host-core 已有 `serde_json::Value`，未引入 bridge-hub 依赖，crate 依赖方向未被破坏。✓

**Blocker 数量结论：1（B1：事件收集路径不可达，host 端点未订阅 topic）。**
建议 B1 修复并补事件路径测试后再进入第 2 批；S1/S2（timeout 失效/持锁阻塞）与 S5（错误静默回落）应在删除回落分支前一并处理，否则单轨化后会放大为不可诊断的超时与错误丢失。
