## 三、问题清单

### Blocker

**B1 — 等待谓词错误 + 失败开放：3/4 命令启动空转 30 秒，spawn 失败静默兜底**

- 位置：
  - `provider.rs:75-81`：`deadline = now + 30s`，循环条件 `host.hub().providers_of("system.listCommands").is_empty()`；循环结束后**无任何 `bail!`**。
  - `hub-stdio.ts:43-53`：`endpointCapabilities()` 只返回切片 plugin 的 `method`，不返回内建方法。
  - `packages/distribution/core/npm/core/lib/known-commands.json`：`needsNodeBridge=true` 的四个命令切片为——`workspace: [compiler, config, lifecycle, lint, toolchain, template, dynamic-commands]`、`product: [product, config, lifecycle, toolchain]`、`pi: [agent, toolchain]`、`tools: [system, dynamic-commands, toolchain, config]`。**前三个均不含 `system`**。
  - `lan.mjs:521-528`：上述清单被原样写成 `LANIA_BRIDGE_SLICES` 注入子进程；`slices.ts:65-67` 非 undefined 即按清单加载，`slices.ts:86-101` 只加载清单内切片。
- 证据链：
  1. `lan workspace` / `lan product` / `lan pi` 启动 → Node 端点 announce 的是 `compiler.dev` / `config.loadLan` / `lint.run` 等，**没有 `system.listCommands`**。
  2. `provider.rs:76` 的谓词永远为 `true` → 循环跑满 30s（`pump_until_idle(50)` + `sleep(5ms)` 反复空转），`new()` 才返回。每次命令调用都付这 30 秒。
  3. 30s 后 `new()` 返回 `Ok`，Hub 中其实**已有** `compiler.dev` 等能力，请求本可正常路由——这 30 秒是纯浪费；而若端点确实没起来（node/tsx/切片缺失），同样等满 30s 后返回一个空 Hub，`call_sync` 回 `E_METHOD_NOT_FOUND`，再被 `bridge_api.rs:142-151` 回落 1:1。**没有任何错误上抛**。
  4. 另一条失败路径：`hub_mode_command()?`（`client.rs:43`）/ `attach_command()?`（`lib.rs:109,114`）在 node 不在 PATH、资产缺失时返回 `Err` → `bridge_setup.rs:58` `if let Ok(provider)` **直接跳过整个 Hub 装配**，`bridge_slot` 保持 `None`，全部走 1:1。注释 `bridge_setup.rs:42-43` 明写"任何一步失败都降级为纯 1:1 回落"。
- 后果：与用户硬要求"不做兼容、不打补丁、不兜底"正面冲突；且"所有使用 `load_bridge_provider` 的命令"中 3 个高频命令被确定性拖慢 30 秒。现有测试不设 `LANIA_BRIDGE_SLICES`（等于 `'*'` 含 system），全部走快路径，**掩盖该缺陷**。
- 反例（可复现）：`LANIA_BRIDGE_SLICES='compiler,config,lint' cargo test -p lania-bridge-host real_node_bridge_announces_full_methods_and_routes` 的 `wait_for` 同样卡满 30s；把同等 env 注入 `HubBridgeProvider::new()` 计时即可稳定复现 ≥30s。
- 改法：等待谓词改为"任一业务 capability 已注册"（暴露 `hub().providers()` 或检查本次 announce 的任一 method），而非写死 `system.listCommands`；超时后 `bail!("E_BRIDGE_ANNOUNCE_TIMEOUT ...")`，让 `configure_command_bridges` 用 `expect`/`Result` 向上传播而不是 `if let Ok` 静默跳过；补一条注入受限切片清单、断言"≤N 秒内完成且失败时返回 Err"的回归测试。

**B2 — `call_sync` 200 轮固定上限（≈200ms）误杀真实业务，回落后 1:1 重复执行**

- 位置：`provider.rs:115` `for _ in 0..200`、`provider.rs:118/124` 两轮 `pump_until_idle(50)`、`provider.rs:153` `sleep(1ms)`、`provider.rs:155` `E_TIMEOUT`；对照 `bridge_api.rs:142-151`（`Ok(Err(err))` → `None`）、`bridge_api.rs:166-170`（`None => dispatch_bridge_request`）。
- 证据链：
  1. `StdioChannel::try_recv`（`channel.rs:132-138`）是非阻塞 `mpsc::try_recv`；无帧时 `pump_until_idle(50)` 第一轮即返回 false。故 200 轮基线与 200×1ms + 少量 pump 开销同阶，约 **200–400ms**。
  2. `policy.timeout_ms` 默认 30s（`context.rs:132-135` + `client.rs:97`），外层 `tokio::time::timeout`（`bridge_api.rs:97-101`）远大于内层；**真正的截止者是内层 200 轮**，外层永远抢不到。
  3. 真实切片方法耗时远超 200ms：`lint.run` 跑 eslint/oxlint/prettier/oxfmt（`contract.test.ts:96-143`）、`compiler.build`、`product.build` 均为秒级。Node 端 `handleExchange` 仍在处理时，Rust 端已 `bail!("E_TIMEOUT: no response for capability ...")`。
  4. 回落路径用**同一份已改写的 `request`**（`bridge_api.rs:85`、`bridge_api.rs:169`）再跑一次 1:1 客户端 → lint/build/dev 被执行**两遍**，dev server 可能被启两次。
- 后果：第 2 批声称"精确路由真实业务"实际只对 <200ms 的 `system.listCommands` 类方法成立；慢业务既没被 Hub 承接，还产生副作用重复执行。新增 E2E 测试只发 `system.listCommands`（`stdio_endpoints.rs:179`），**完全没有覆盖慢方法**，是典型绿灯假象。
- 反例（可复现）：对真实 Node 端点 `call_sync("lint.run", {cwd, ...})` 或在 `onRequest` 里人为 `await setTimeout(1000)`，断言返回 result，必然拿到 `E_TIMEOUT`。
- 改法：把 `0..200` 换成与 `policy.timeout_ms` 对齐的 `deadline: Instant`，循环内 `Instant::now() < deadline`；或把 `call_sync` 改成 async 轮询 + `tokio::time::sleep` 并放入 `spawn_blocking`，让外层 timeout 真正可取消（同时修第 1 批 S1/S2）；补一条"慢方法在 >200ms 后仍能拿到响应"的测试。

## 四、红队重点反例逐条回答

**1. `new()` 同步等 30s 是否拖慢/卡死？spawn 失败降级是否违反"不兜底"？**
→ **是，且是确定性的，不是理论风险**。等待谓词写死 `system.listCommands`（`provider.rs:76`），而 `known-commands.json` 中 `workspace`/`product`/`pi` 的切片清单都不含 `system`，announce 永远不会命中 → 每次命令启动空转满 30s（B1）。`#[tokio::main]` 是多线程，所以不会卡死整个 executor，但命令首屏被阻塞 30s。spawn 失败经 `hub_mode_command()?`/`attach_command()?` → `bridge_setup.rs:58 if let Ok` 静默跳过 → 100% 回落 1:1；30s 超时也不报错继续。**两条都是兜底，直接违反硬要求**。

**2. `host.subscribe("event.*")` 与真实 Node 端点 subscribe 的关系；事件能否真从 Node 流到 host？**
→ 订阅侧**通**：`provider.rs:65` → `hub.rs:290-302 topic_index`，`topic_matches("event.*","event.progress")` 成立，第 1 批 B1 已修复并经 `host_receives_published_events_via_subscription` 验证。但**源侧断**：Node 端 `onRequest` 不传 `emit`、丢弃 `exchange.events`（`hub-stdio.ts:64-68`），`onEvent` 空（`:79-81`），所以真实业务**没有任何 Publish 帧产生**，host 永远收不到 Event。`endpointCapabilities`/announce 里的 `['event.*']`（`hub-stdio.ts:86`）只是让 Node 订阅 host 方向的事件，与"Node → host"无关，且 Node 侧 `onEvent` 不处理。结论：**事件不能从 Node 流到 host**；batch1 的事件流接口目前只对测试注入的 emitter 有效。

**3. `hub_mode_command` 的 `endpoint_id` 是否所有调用点一致？**
→ **一致**。`provider.rs:33 NODE_ENDPOINT_ID="node-hub"` → `:70 hub_mode_command(NODE_ENDPOINT_ID)` + `:71 attach_command(NODE_ENDPOINT_ID, ...)`；E2E 测试 `stdio_endpoints.rs:158,160` 同样用 `"node-hub"`。`client.rs:52` 写 `LANIA_ENDPOINT_ID`，`runtime.ts:87 endpointIdFromEnv` 读取该 env，与 `attach_channel` 的 id 对齐，`hub.rs:227-230` 的坏帧校验可通过。仅 N3 的常量重复问题。

**4. 完整 method announce 与 `onRequest` 的 params 透传是否正确，cwd 会不会丢？**
→ 主干**正确**：`hub.rs:369` 原样透传 `params` → `runtime.ts:68 frame.params` → `hub-stdio.ts:67`，普通 `{cwd, ...}` 能到达 `handleExchange`。但 `?? request` 的双击解包是隐患（S2）：参数对象自带 `params` 键时会丢掉包括 `cwd` 在内的兄弟字段。此外 E2E 测试只发 `json!({})`（`stdio_endpoints.rs:179`），**没有验证任何真实需要 cwd 的方法**（config.loadLan / lint.run / compiler.dev），所以"cwd 不丢"目前只有纸面推导，没有测试证据。

**5. 推迟删回落的决策是否正确，有无更好做法？**
→ **决策方向正确**（此刻删回落会让事件/反向 RPC 功能灾难，违背"事件不退化"）。但**理由不完整**：FR-4 理由（`spec.md:17-19`）把"事件源未接通"和"hostRPC 未接通"并列为阻塞项；实际上事件**不需要**等 hostRPC——`runtime.ts:39` 已有 `publish`，只要在 `runHubEndpoint` 创建 `runtime` 后把 `emit` 设为 `async (e) => runtime.publish(e.method, e.params)` 并传给 `handleExchange`（`hub-stdio.ts:64`），配合 host 端已订阅的 `event.*`（`provider.rs:65`），事件链路即可在**本批内**闭环。真正的硬阻塞只有 hostRPC（Node 反向调用 fs/git/exec）。更好的做法：本批先把事件 publish 接通并补"慢方法 + 事件非空"的 E2E 断言，把"删回落"精确推迟到 hostRPC 接通之后；同时修正 AC-3，避免口径分裂。

**6. dist gitignore 是否造成交付契约不一致？**
→ **是潜在风险，当前未爆但无防线**（S5）。干净 checkout 走 src/tsx，源码是新的，正确；但 `process.rs:446` 只要 dist 存在就优先且**不校验内容**，旧 dist 会让 announce 退回前缀、B1 全量触发。FR-2"重新编译 dist"是人工步骤，未固化为构建门禁。总包 `slices: []` 的配置也埋着"零切片"雷。
