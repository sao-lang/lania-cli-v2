## 3. 红队新问题

以下按用户指定的 5 个核查点逐一回答，并给出额外发现。

### W1（P1，建议重点跟踪）：总包 `lan` 路径下 Node 子进程不保证被显式 kill

**核查问题：new() spawn 真实 Node 后，每个命令进程都多一个常驻子进程——Drop 是否可靠 kill？**

结论：**分路径，命令子包可靠，总包不可靠（有缓解，非零风险）。**

- 可靠侧：`BridgeHost` 持有 `children: Vec<Child>`，`shutdown()`（lib.rs:193-199）逐进程 `kill() + wait()`，`Drop`（lib.rs:202-206）调用 `shutdown()`。6 个命令子包 bin 以 `Result` 正常返回，栈展开触发 `HostRuntime → bridge_slot → Arc<HubBridgeProvider> → BridgeHost` 的 Drop 链，**kill 可靠**。
- 不可靠侧：总包 `lania-cli/src/main.rs` 在 4 处调用 `std::process::exit()`（:140, :177, :204, :228），**该调用不运行任何 Rust Drop**。且在此之前调用的 `host.shutdown_async()`（lifecycle.rs:97-126）只清理 `services.node_bridge`（1:1 客户端，:122）与 `services.bridges`（1:1 兼容层，:123），**未 take/drop `bridge_slot`**（`runtime.rs:87`）。因此 Hub provider 的 Arc 在 `process::exit` 时仍被持有，`BridgeHost::drop → shutdown()` 不会执行。
- 缓解机制：Node 端 `stdio.ts:29-32` 在 hub 模式下 `await runHubEndpoint(); process.exit(0);`。父进程退出关闭 stdin 管道后，`runtime.run()` 的 `for await` 遇 EOF 结束 → finally 收尾 → `process.exit(0)` 自行退出。故正常短命令不会留下永久孤儿进程。
- 残留风险：若 Node 端正处于不可中断的长任务/同步 IO，stdin EOF 不能保证及时触发 self-exit；Windows 下管道句柄关闭语义亦不如 POSIX 直接。此时可能残留子进程。

**建议**：在 `shutdown_async()` 中显式 `take()` 并 drop `bridge_slot`（或给 `BridgeSlot`/`BridgeProvider` 增加显式 `shutdown()`），使总包路径在 `process::exit` 前主动 kill，而非依赖对端 self-exit。此项不阻断本批功能，但属资源生命周期正确性问题，建议列 P1 跟踪。

### W2（P2）：`LANIA_TIMEOUT_MS` 对 Hub 路径失效；B2 因同步阻塞而「意外」不被该配置破坏

**核查问题：call_sync deadline 是否真的替代固定轮数（有没有残留 200）？**

替代已完成（见 §2），无残留。但发现关联问题：

- `bridge_api.rs:97-101` 用 `tokio::time::timeout(policy.timeout_ms, provider.call(...))` 包裹 Hub 调用；`policy.timeout_ms` 来自 `ExecutionPolicy::from_env`（context.rs:125-144），可被 `LANIA_TIMEOUT_MS` 覆盖，默认取 `node_bridge.timeout()`。
- `provider.call()`（provider.rs:180-187）内部直接调用**同步阻塞**的 `call_sync()`（持 Mutex、循环 `pump + sleep`），全程无 `.await` 让出点。tokio 的 timer 在该 future 返回 Ready 之前没有机会被 poll，因此外层 `timeout` 在 Hub 命中路径上**实际不会触发**。
- 影响两面：
  - 正面：即使 `LANIA_TIMEOUT_MS` 被设得小于 30s（如 CI 调试设 5s），也不会在 5s 时误触发「回落 → 1:1 重复执行」，B2 的修复不会以另一种形式复现。
  - 负面：`LANIA_TIMEOUT_MS` 这一对外承诺的超时配置在 Hub 路径上失效，实际超时恒为 `CALL_TIMEOUT=30s`。且同步阻塞占住 tokio worker 线程最长 30s。

**建议**：在文档/配置说明中标注该限制，或在后续批次将 `call_sync` 改造为可让出的异步实现，使 deadline 与 `policy.timeout_ms` 单一来源化。

### W3（P3）：多处单元测试与本机 Node/tsx 环境耦合

**核查问题：configure_command_bridges 改 Result 后，测试里的 .expect 是否会在无 Node 环境失败？**

会。`bridge_setup.rs:97, :112` 的 `.expect("configure bridges")` 会进入 `load_bridge_provider() → HubBridgeProvider::new()` → spawn 真实 Node + 等 announce；无 Node/tsx 或 dist 资产缺失时 30s 后 panic。`provider.rs` 中 `provider_routes_without_naming_a_language`（:293）、`language_registration_is_opaque`（:302）、`host_receives_published_events_via_subscription`（:313）、`declared_capability_is_routable_after_language_registration`（:332）同样用 `HubBridgeProvider::new().unwrap()`。

- 这与该文件专门提供的 `provider_without_node()`（:233）隔离构造的设计意图不一致。
- 当前基线（bridge-host 5+6、lania-host 73 全绿）说明 CI 环境具备 Node/tsx/dist，故**不是本批 Blocker**。
- 但在离线/无 Node 的开发者机器上，`cargo test --workspace` 会出现失败的测试，属于可移植性退化。建议后续把这些测试改用 `provider_without_node()` 或统一的测试用 provider 注入点。

### W4（P3）：`bridge_setup.rs` 文档注释与代码行为矛盾

`bridge_setup.rs:42-43` 仍写「任何一步失败都降级为纯 1:1 回落……保证 smoke-pi 等行为不退化」，但修复后的代码（:58-63）已改为「失败即报错、不回落」。这是**过时注释**，会误导后续维护者以为仍有兜底。建议改为「Hub 装配失败即让命令失败」。

同类需明确的注释：`bridge_setup.rs:8-9, 34-36, 49-50`、`bridge_api.rs:88-94, 142-169` 中关于「回落/兼容层」的描述——这些属于**第 3 批待删范围**，与用户「删回落推迟到第 3 批」的计划一致，本轮不作为 Blocker，但应确保第 3 批有明确的清除清单。

### W5（P3）：内建命令也被强制拉起 Node

总包 `main.rs:93` 的 `configure_command_bridges` 位于内建命令渲染（:127 `render_builtin_command`，含 `--help/--version`）之前。因此 `lan --help` 也会先 spawn Node 并等 announce（当前约 389ms；无 Node 环境下会 30s 超时失败）。这是 B1 fail-fast 硬要求的直接后果，功能正确但可用性退化，建议评估是否把内建命令短路提前到 provider 装配之前。
