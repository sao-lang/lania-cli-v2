## 1. 删回落改动正确性审查

### 1.1 `bridge_api.rs`：三种失败路径

新实现（`bridge_api.rs:91-125`）：

| 分支                             | 代码位置   | 返回                                                                     | 恰当性                                                                                                                                                      |
| -------------------------------- | ---------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| provider 未注入（`None`）        | `:91-97`   | `ExecutionError{EXIT_RUNTIME_ERROR, "…no 1:1 fallback"}`                 | ✅ 恰当。所有命令 bin 已对 `configure_command_bridges(...).await?` 加 `?`（`lan-tools.rs:42`、`main.rs:93` 等），正常路径 `None` 不可达；作为防御性失败合理 |
| `Ok(Err(err))` provider 调用失败 | `:105-114` | `ExecutionError{EXIT_RUNTIME_ERROR, "…failed: {err} (no 1:1 fallback)"}` | ✅ 恰当，但**丢失结构化错误码**（见 1.2）                                                                                                                   |
| `Err(_)` timeout                 | `:115-124` | `ExecutionError{EXIT_RUNTIME_ERROR, "…timed out … (no 1:1 fallback)"}`   | ⚠️ 失败方式恰当（不再兜底），但**exit code 语义退化**（见 1.2）                                                                                             |

三处均显式 `return Err(...)`，没有把错误降级成 `Ok`。委托给 Hub 的命名、参数与 before-hook 改写边界（`:42-86`）保持不变。

**结论：删除回落的方式本身正确。** 三种失败都是"响亮失败"，不是静默降级。

### 1.2 exit code 语义：未保留（Should S1）

这是用户点名要确认的点，答案是**没有保留**：

1. 原 `dispatch_bridge_request` 在超时耗尽重试后返回 `EXIT_TIMEOUT = 124`（`requests.rs` 旧 `:105-115`）；新路径统一返回 `EXIT_RUNTIME_ERROR = 2`。124 → 2 是可观察的 CLI 行为退化，脚本无法再区分"超时"与"一般运行时错误"。
2. `raise_bridge_error`（`requests.rs:18-45`）是全局唯一把 `E_TIMEOUT` 映射为 `EXIT_TIMEOUT`（124）的地方。但新 `call_bridge` 构造 exchange 时硬编码 `error: None`（`bridge_api.rs:150-157`），因此 `:209` 的 `raise_bridge_error(...)?` **永远 no-op**，124 映射成为死代码。
3. 更深层：`provider.call_sync` 把 Hub 的 `BusErrorDetail{code, message}` 在 `provider.rs:211-213` `bail!` 成纯字符串，`E_TIMEOUT` 等原始 code 在进入 `call_bridge` 前已丢失，即使想映射也无据可依。

**顺带确认 retry 策略丢失**：原 `dispatch_bridge_request` 有 `for attempt in 0..=retry_attempts` 重试循环，新 `call_bridge` 单次 `timeout` 即失败。`policy.retry_attempts` 在 Hub 路径不再生效（Hub 侧仅有 `CALL_TIMEOUT=30s` 的轮询截止，`provider.rs:180`）。retry 不是兜底，属韧性策略退化（并入 S1）。

## 5. 分级清单

### Blocker（1）

**B1 —— "Hub 100% 承接"目标未达成：多语言 lint/build 仍由 1:1 `call_runtime_bridge` + 显式 fallback 服务。**

- 解除条件：见 3.4 最小清单 1–5。

### Should（6）

- **S1** exit code 语义未保留：`timeout` 由 124（`EXIT_TIMEOUT`）退化为 2；retry 策略丢失；`raise_bridge_error` 死代码（`bridge_api.rs:115-124,150-157,209`；`requests.rs:25-29`）。建议显式区分 timeout/失败，并保留原始 error code 结构。
