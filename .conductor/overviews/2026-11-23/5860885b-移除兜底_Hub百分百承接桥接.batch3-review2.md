## 1. B1（hostRPC 反向通道挂起）—— 确认关闭 ✅

### 1.1 修复确实在运行（关键前提，已验证）

`process.rs:437-460` 的 `bridge_launch_spec_for_dir()` **优先选择 `dist/entry/stdio.js`**，仅当 dist 缺失才回退 src。我核验了 `dist/entry/hub-stdio.js:108-137`，它与 `src/entry/hub-stdio.ts:123-154` 的修复内容逐行等价（立即返回 + Promise.race + 30s timer + unref + catch 里 handleHostResponse）。

> 红队检查点：源码修了但 dist 没重新构建，是这类修复最常见的“假关闭”。本项 **通过**——dist 与 src 同步。但需把“发布前必须重建 dist”列为流程约束（见 §5 C-5）。

### 1.2 30s 超时为何现在真的有效（时序推演）

`host-rpc.ts:118-135`：

1. `transport.write()` 在 `hub-stdio.ts:152` 立即 `return Promise.resolve()`；
2. `hostCall` 随即执行 `return await promise`（`host-rpc.ts:135`），进入自己 30s 超时（`host-rpc.ts:120-126`）的消费点；
3. 真正的等待发生在 `void (async()=>{...})()`（`hub-stdio.ts:128-151`），与 hostCall 解耦。

**双超时竞态（两处都是 30s）不会 double-settle**：

- hostCall 的 timer 先注册（`host-rpc.ts:120`），race 的 timer 后注册（`hub-stdio.ts:133`），前者先触发。
- 先触发者调用 `handleHostResponse`（晚到者经 `pending.delete(id)` 后 `pending.get(id)` 返回 undefined，`host-rpc.ts:90-92` 直接 return）——**幂等，无二次 resolve/reject**。
- 反向顺序（race timer 先触发）也安全：catch 调 `handleHostResponse({id, error})` → `clearTimeout(hostCall 的 timer)`（`host-rpc.ts:93-95`）→ reject `E_HOST_RPC_TIMEOUT`。hostCall 的 timer 已被清掉，不会重复。

### 1.3 timer.unref 是否有问题 —— 无问题

race 的 timer 调用了 `timer.unref?.()`（`hub-stdio.ts:137`），但：

- hostCall 的 timer **没有** unref（`host-rpc.ts:120-126`），它足以撑住事件循环到 30s；
- `runtime.run()` 持有 stdio 事件循环。
  因此进程不会因 unref 提前退出导致超时永不触发。unref 在此处是**正确用法**（避免 race timer 单独延长进程生命周期）。

### 1.4 unhandled rejection —— 无残留

- `void (async()=>{...})()` 内部 `try/catch` 覆盖全程，包括 `handleHostResponse` 调用；async IIFE 不会 reject，`void` 安全。
- `Promise.race` 会给传入的 timeout-promise 附加 reject handler（race 内部 `then(onFulfilled, onRejected)`）。即便 `runtime.request` 先 resolve、30s 后 timeout-promise 迟到 reject，该 reject **已有 handler**，不会升级为 unhandled rejection。

### 1.5 B1 的次要瑕疵（非 Blocker）

- **M-1（Minor）**：race 的 timer 在 `runtime.request` 正常 resolve 后**未 clearTimeout**（`hub-stdio.ts:130-139` 无 finally 清理）。迟到 reject 虽被吞，但闭包被持有 30s。unref 后最终释放，仅轻微资源占用。建议加 `finally { clearTimeout(timer) }`。
- **M-2（Minor）**：超时后 Node 侧 `runtime.request` 自身的 pending 条目无人清理（EndpointRuntime 的 pending 表无超时）。每次超时泄漏一个条目，长生命周期进程下缓慢累积。需 runtime 层支持 cancel/timeout 清理。

**B1 判定：关闭。** 挂起路径已被两层 30s 兜住，不存在永久挂起。

## 2. B2（长任务事件丢失 + shutdown 停错进程）—— 确认关闭 ✅

### 2.1 运行期事件泵：25ms 是否够 —— 够

- `lib.rs:90-97` 新增 `drain_events()` 默认空实现，契约清楚（长任务 response 先返回、事件随后到达）。
- `provider.rs:270-284` 覆盖实现：`pump_until_idle(50)` 后 `while let Some(frame) = client.try_recv()` 排空所有 `BusFrame::Event`。
- `long_running.rs:68-86` Hub 路径 `tokio::select!` 每 25ms 调一次 `drain_events()`。

**关键判断**：`drain_events` 每次调用排空的是 Hub 队列中**当前全部**事件，因此 25ms 只决定**显示延迟**（≤25ms），不决定**是否丢失**。只要事件进了 Hub 队列，下一 tick 必被取出。事件不丢，B2 的事件丢失部分关闭。

### 2.2 shutdown 是否停对进程 —— 是

`long_running.rs:110-138`：Hub 路径（有 provider）改用 `provider.call(&stop.method, stop.params)`，与业务请求走**同一个 provider / 同一个 Hub**，命中真正在跑的 Node dev 端点，不再经 `node_bridge.compiler_stop_request()` spawn 新的 1:1 进程（`activeCompiler=null` 的旧病灶）。
1:1 回落分支完整保留在 `long_running.rs:139-142`（`self.dispatch_bridge_request(...)`），仅在 provider 为 None 时走，链路未被破坏。

### 2.3 compiler.stop 的 response.error 语义 —— 有差异，但不是 Blocker（见 C-1）

`long_running.rs:122` 硬编码 `error: None`。这不是疏漏而是与 Hub 单轨设计自洽：

- `provider.rs:210-213`：`call_sync` 收到 `BusFrame::Response { error: Some(detail) }` 时直接 `anyhow::bail!("{code}: {message}")`，不会把 error 作为 `BridgeProviderExchange` 的一部分返回；
- 因此 `long_running.rs` 的 `provider.call(...).await?` 要么成功（error 必为 None），要么返回 Err 上抛，`error: None` 的硬编码在当前契约下**语义正确**。

但与 1:1 存在可观察差异：1:1 路径下 compiler.stop 的 `response.error` 会保留到 `call_bridge:226` 的 `raise_bridge_error`，其中 `E_TIMEOUT → EXIT_TIMEOUT`（`requests.rs:29-33`）。Hub 路径下同一错误变成普通 `anyhow!`（`long_running.rs:117`），**丢失 exit code 分类**。详见 C-1。

### 2.4 B2 判定

**关闭。** 事件不丢、shutdown 停对进程、1:1 回落完整。编译/类型无新增问题（cargo check rc=0 与本次代码审阅一致，`drain_events` 为同步方法不涉及 async_trait 的 Send 约束，MutexGuard 不跨 await）。

## 3. 红队新发现（按严重度分级；本轮无 Blocker）

### C-1（Concern，建议本批处理）Hub 路径 compiler.stop 错误丢失 exit code 分类

- 位置：`long_running.rs:110-138` + `provider.rs:210-213` + `requests.rs:22-49`
- 事实：Hub 路径把 provider 的 Err 经 `anyhow!` 上抛（`long_running.rs:117`），绕过 `raise_bridge_error` 的 `E_TIMEOUT → EXIT_TIMEOUT` 映射。
- 影响：长任务停止阶段若发生超时，最终 exit code 从 `EXIT_TIMEOUT` 退化为通用 runtime error。属失败路径的可观察性/退出码退化，不影响正常路径，**不升级为 Blocker**。
- 建议：在 `map_err` 中识别 `E_TIMEOUT` 并构造带 `BridgeError` 的响应，或复用 `raise_bridge_error` 的统一映射。

### C-2（Concern）Hub 路径 shutdown 后没有尾事件排空

- 位置：`long_running.rs:143-158` 的 2s 排空被 `if let Some(call) = active.as_mut()` 守卫；Hub 路径 `active=None`，该段不执行。
- 影响：compiler.stop 之后端点可能继续 publish 少量退出/编译日志，这些尾事件在 Hub 路径丢失。1:1 路径能排到。
- 补充：`call_bridge:224-227` 对 `follow_up.exchange.events` 只做 `raise_bridge_error`，**未调用 `apply_bridge_events`**——这一点 1:1 与 Hub 共有，非本批引入，但 Hub 因缺少 2s 排空而更明显。
- 建议：Hub 路径在 stop 后调度一次短时 `drain_events` 排空（复用同一 2s 窗口）。

### C-3（Concern）`drain_events` 的 Mutex lock 失败静默返回空集

- 位置：`provider.rs:273-275`：`let Ok(mut state) = self.state.lock() else { return Vec::new(); };`
- 事实：与同文件 `lock()`（`:167-169`，返回 `anyhow error`）以及 `shutdown()`（`:265-267`，静默）策略不一致。poison 时**静默丢事件且无任何日志**。
- 影响：poison 只在 panic 后发生，属异常路径；但静默使故障不可诊断。红队问题清单中此点属实。
- 建议：至少记一条 Warn 日志；或改为 `self.lock()` 上抛让调用方感知。

### C-4（Concern）事件解析失败静默丢弃，可观测性不一致

- 位置：`long_running.rs:75-83`（运行期泵）与 `:128-135`（stop 响应事件）使用 `if let Ok(...)` / `filter_map(...ok())`，**无日志**。
- 对照：`bridge_api.rs:115-123` 主路径对同类失败有 `drop undecodable hub event: {method}` 的 Warn。
- 影响：事件结构漂移时无诊断线索。属实，建议对齐 Warn 日志。

### C-5（Concern）host RPC 的 events 在 Hub 路径被丢弃

- 位置：`provider.rs:52-68` 的 `HostRpcHandlerBridge::on_request`：`Ok((result, _events)) => Ok(result)`。
- 对照：1:1 的 `process.rs:300-307` 把 handler 返回的 `(result, events)` 一并写进 `HostResponse.events`。
- 事实：`BusFrame::Response` 结构本身无 events 字段（`provider.rs:194-202`），所以不是“忘了传”，而是协议层不支持。
- 影响：Node 侧 `hostCall()` 拿到的 `HostExchange.events` 在 Hub 路径恒为空（`host-rpc.ts:100-103`），任何依赖 host 能力事件流的逻辑（如 `schema-tools.ts:457` 的 emitBridgeEvents）收不到。
- 建议：确认业务是否依赖；若依赖，需在 BusFrame Response 增 events 字段并透传，或在 host 能力层把事件降级为 publish 的 Event 帧。

### C-6（Minor）src/dist 双份产物必须同步

- B1 的修复同时改了 src 与 dist 才生效。后续任何 hub-stdio.ts / host-rpc.ts 修改都必须重建 dist，否则运行入口（`process.rs:446`）仍跑旧逻辑。建议纳入 CI 产物一致性检查。

## 4. 能否安全删除 call_bridge 的 1:1 回落 —— 不能 ❌

### 4.1 仍在依赖回落的关键路径

`bridge_api.rs:95-170`：provider 返回 `E_METHOD_NOT_FOUND`（`:142-152`）或超时（`:153-161`）时记 Warn 并回落 `dispatch_bridge_request`（`:169`）。这些失败当前被回落掩盖，一旦删回落将直接暴露为 `ExecutionError`。

### 4.2 S4 前置未解决：bridge.\* 内建方法确实没有 Hub provider（独立证据链）

1. `hub-stdio.ts:45-56` / `dist:36-47` 的 `endpointCapabilities()` **只收集 `plugin.methods`**，注释声称“内建方法在 Hub 侧由宿主提供”。
2. 但宿主侧 `provider.rs` 实际 attach 的端点只有三类：
   - `host-rpc`（`:117-122`），announce **仅 `host.*`**；
   - `register_language` 的 echo 端点（`:251-256`），`PROVIDES = ["echo.ping", "echo.upper"]`（`adaptors/rust/endpoint.rs:43`）；
   - `node-hub`（`:128-129`），announce 仅插件方法。
     **没有任何端点声明 `bridge.*`。**
3. `handleBuiltinRequest`（`builtin-handlers.ts:38-138`）虽能处理 `bridge.ping/shutdown/metrics/subscribe/heartbeat/plugins.resolve`，但 `makeHubHooks`→`handleExchange`（`index.ts:29-36`）能否被调用，前提是 Hub 先把请求路由到 node-hub；而 Hub 的 `route_request`（`hub.rs:360-394`）是 `capability_index.get()` **精确匹配**，通配回退只有 `host.*`（不匹配 `bridge.*`）→ 回 `E_METHOD_NOT_FOUND`。
4. 结论：宿主经 Hub 调任何 `bridge.*` 内建方法必然失败 → 当前靠回落兜住。**删除回落 = 这些方法直接不可用。** 这与上轮 S4 的判断一致，且本轮已独立复现其根因。

### 4.3 删除回落前必须完成的前置清单

1. **补齐 bridge.\* 的 Hub provider**：宿主侧 attach 一个声明 `bridge.ping/bridge.shutdown/bridge.metrics/bridge.subscribe/bridge.heartbeat/plugins.resolve` 的进程内 handler，语义复用 `handleBuiltinRequest`；或让 node-hub 把 `BRIDGE_METHODS` 纳入 announce 并确认 `handleExchange` 的 builtin 分支在 Hub 路径可达。
2. **覆盖 toolchain.describe 等 schema-tools 方法**：`bridge_api.rs:353-385` 的 `toolchain_command` 目前仍走 `node_bridge()` 1:1 客户端；删回落后需确认这些 capability 在 Hub 能力表中有归属。
3. **确认 compiler.stop 的全场景可路由性**：覆盖 stop 在长任务/非长任务、provider 超时等分支的行为（与 C-1 一并处理）。
4. **处理 C-5 的 events 丢失**（若业务依赖）。
5. **建立 capabilities 全覆盖的守卫测试**：断言“宿主可能发起的所有 method 集合 ⊆ Hub 已声明 capability 集合”，否则删回落会引入静默回归。
