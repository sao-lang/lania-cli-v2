## 一、B1 关闭确认：逐环节证据链

B1 的原始断点：host 端点从未订阅 topic → Hub 无订阅者 → `client.try_recv()` 收不到 `BusFrame::Event` → 收集分支死代码。逐环节核对如下。

### 1. `client.subscribe("event.*")` 是否真注册进 `topic_index` — 成立

- `provider.rs:62` `client.subscribe("event.*")` → `endpoint.rs:48-50` `Endpoint::subscribe` → `runtime.subscribe(topic)` 向 client 的 outgoing channel 写入 `BusFrame::Subscribe { topic }`。
- `provider.rs:63` `host.pump_until_idle(50)` → `BridgeHost::pump_until_idle`（`lib.rs:181-183`）→ `BridgeHub::pump_until_idle`（`hub.rs:212-218`）→ `pump_once` → `route_frame` → `hub.rs:233` `BusFrame::Subscribe { topic } => self.add_subscription(from, topic)`。
- `hub.rs:290-302` `add_subscription`：`slot.subscribes.push("event.*")` 且 `topic_index.entry("event.*").or_default().insert("host")`。**`host` 确实进入 `topic_index`**。
- 时序：`subscribe` 与 `pump_until_idle` 在同一线程内同步顺序执行，帧先入队后 pump；`pump_until_idle` 循环至 `pump_once` 返回 false（无进展），Subscribe 帧必在第一轮被取走并路由。**无竞态、不依赖调度**。

### 2. `event.*` 能否匹配 `event.progress` / `event.log` — 成立

- `hub.rs:402-407` `topic_matches(pattern, topic)`：`pattern.strip_suffix('*')` 取前缀，再 `topic.starts_with(prefix)`。
- `event.*` → 前缀 `event.`；`event.progress` / `event.log` / `event.dev_url` 等均以 `event.` 开头 → 匹配为 true。✓
- `hub.rs:311-313` `broadcast` 校验的是 **publish 的 topic** 不得含 `*`；`event.progress` 不含 `*`，合法。订阅侧 `event.*` 含 `*` 是通配，合法。✓
- 边界：`event.*` 不匹配裸 `event`（无 `.`）；真实事件 topic 均为 `event.<name>`，不受影响。Nit 级，见 §三 N1。

### 3. Hub 是否真把 Event 投递到 client — 成立

- 语言端点 publish → `BusFrame::Publish` → `hub.rs:235` → `broadcast("lang-*", "event.progress", payload)`。
- `hub.rs:317-326` 遍历 `topic_index`，`topic_matches("event.*", "event.progress")` 命中，`subscribers={"host"}`；`broadcast_to_self` 默认 false（`hub.rs:48,68`）但发布者是 `lang-*` ≠ `host`，故 `targets` 包含 `host`。
- `hub.rs:328-335` `send_to("host", BusFrame::Event { topic, payload, from })` → 写入 host 侧 channel。
- `provider.rs:107-124` `state.client.try_recv()` → `endpoint.rs:77-82` 从同一 channel 取帧 → `BusFrame::Event { topic, payload, .. }` → `events.push(...)`。**收集分支由不可达变为可达**。✓

### 4. 新增测试是否真验证事件路径（非恒空断言）— 成立

`provider.rs:211-228` `host_receives_published_events_via_subscription`：

- `HubBridgeProvider::new()` → `emitter = state.host.attach("emitter")` → `emitter.publish("event.progress", ...)` → `state.host.pump_until_idle(50)` → `state.client.try_recv()`。
- 断言 `matches!(received, Some(BusFrame::Event { .. }))`：若订阅/广播任一环断开，`try_recv()` 返回 `None`，测试失败。该断言**必须真实走通订阅→广播→投递**才能通过，不是 `assert!(vec.is_empty())` 式恒空。✓
- `event.*` 前缀与 `event.progress` 的匹配在这条测试里被实际执行（`broadcast` 的 `topic_matches` 分支），不是纸面推导。✓

> **判定：B1 关闭。** 修复触及了根因（订阅缺失），且测试能证伪。上一轮 B1 提出的「源侧/订阅侧双断」中，订阅侧已接通；源侧（真实端点 publish）仍属后续批次，见 §三 S3（非本批 Blocker）。

## 二、S5 修复与 Warn 分支核对

`bridge_api.rs:142-161`：原 `_ => None` 拆为 `Ok(Err(err))` 与 `Err(_)` 两支，各记一条 `LogLevel::Warn`。

- **编译**：`err` 为 `anyhow::Error`，`format!("...{err}")` 用 Display，合法（`provider.rs:127` 已同款用法）；`Err(_)` 忽略 `tokio::time::Elapsed`，合法。`self.bridge_provider()` 返回 `Option<&Arc<...>>`（`context.rs:237-239`），与闭包/分支内 `self.log(...)` 同为共享借用，无借用冲突。三包测试全绿佐证。✓
- **行为变化**：两支返回值仍为 `None`（继续回落 `dispatch_bridge_request`），未改变控制流；仅新增日志副作用。✓
- **语义**：`Ok(Err)` 文案「provider call failed」、`Err(_)` 文案「timed out after Xms」区做到了可诊断，S5 的「静默回落」已缓解。✓
- **保留**：`Err(_)` 的 timeout 文案有误导性——`tokio::time::timeout` 对同步阻塞的 `call_sync` 实际不生效（S1），该分支极难命中；一旦命中也未必是真实超时。见 §三 S2。

## 三、红队新发现与遗留问题

本轮改动**未引入新 Blocker**。以下为 Should / Nit，含上一轮未修复项的状态更新。

### Should

**S1 — 上一轮 B1 建议的端到端测试未补：`call_sync` 事件返回路径仍无测试覆盖**

- 位置：`provider.rs:211-228`（新测试只到 `state.client.try_recv()`）、`provider.rs:89-137`（`call_sync` 收集与 `BridgeProviderExchange::new(..., events)` 返回）。
- 上一轮 B1 改法明确要求「补一条『端点 publish → `call_sync` 返回 events 非空且有序』的测试」。本轮新增测试验证了**订阅→广播→投递**这一跳，但没有经过 `call_sync`，未断言 `BridgeProviderExchange.events` 非空。
- 影响：`call_sync` 的 match 分支（`provider.rs:107-124`）、drain 循环去 `break` 后的收集逻辑（`provider.rs:107-124`）、`events` 随 exchange 返回（`provider.rs:129-132`）均无测试保护。这几处代码人工审阅逻辑正确，但一旦后续误改（如把去 `break` 改回、或把 Event 分支漏掉）没有回归网。
- 改法：新增 `custom_handler_publish_reaches_call_sync`：用能 publish 的自定义 `Handler` 注册，调用 `call_sync`，断言 `exchange.events` 非空且顺序正确。

**S2 — `tokio::time::timeout` 对 provider 分支仍失效；本轮 timeout Warn 文案放大误导（上一轮 S1 未修）**

- 位置：`bridge_api.rs:97-101`（`timeout(..., provider.call(...))`）、`provider.rs:141-149`（`call` 内直接同步 `call_sync`）、`bridge_api.rs:153-161`（本轮新增 timeout Warn）。
- `call_sync` 同步阻塞（`pump_until_idle` + `serve_until_idle` + `std::thread::sleep`，`provider.rs:96-135`），在 `async_trait` future 内一次跑完不 yield。外层 `timeout` 无法在中途打断；持锁期间阻塞 tokio worker。
- 本轮新增的 `format!("hub provider call timed out after {}ms, falling back", ...)` 暗示超时机制在工作，实际该分支几乎不可达，读者会被误导。
- 改法：`spawn_blocking` 包裹 `call_sync`，或 future 内以 `Instant` deadline 显式检查并 `tokio::time::sleep` yield；timeout 文案改为「未在 deadline 内完成」以免与实际机制脱节。

**S3 — 生产路径 events 仍恒空：注册的 `EchoHandler` 不 publish 事件（边界说明，非本批 Blocker）**

- 位置：`provider.rs:163-168`（`register_language` 挂 `EchoHandler::default()`）、`adaptors/rust/endpoint.rs:16-40`（`on_request` 只回 response，`on_event` 空实现）、`provider.rs:233-244`（`declared_capability_is_routable_after_language_registration` 断言 `events.is_empty()`）。
- B1 修复使「机制」可达，但通过 `load_bridge_provider()` 装配的真实 provider 所挂端点不会 publish 任何事件，故生产路径 `call_sync` 返回的 events 仍为空。这是事件**源**缺失，属后续批次（真实语言端点接入）；与 B1 的订阅缺口性质不同，不构成对 B1 修复的否定。
- 建议：在 `host-core`/spec 中明确「第 1 批仅打通事件承载机制，源侧 publish 在下批接入」，并保留 S1 的端到端测试作为下批验收前置。

**S4 — 事件无相关性过滤 + 收到匹配 Response 即 return，迟到/跨请求事件会混入或丢失**

- 位置：`provider.rs:117-121`（`BusFrame::Event { topic, payload, .. }` 丢弃 `from`，不按 correlation 过滤）、`provider.rs:125-133`（`if let Some(outcome)` 立即 `return`）、`bridge_api.rs:106-126`（全量转 `BridgeEvent` 渲染）。
- 具体反例：
  1. host 订阅 `event.*` 会收到**所有**端点的事件（`from` 被丢弃）。若某端点在请求之外主动 publish（如 heartbeat / watch 后台事件），会被算进下一次 `call_sync` 的 events，污染渲染。
  2. 若端点先 `respond` 后 publish，或事件跨多轮 pump 才到达，收到匹配 Response 的那一轮立即 `return`（`provider.rs:125`），后续到达的事件**永久丢失**。契约「events 先于 response」依赖端点产生顺序，未被强制。
- 当前 `EchoHandler` 不 publish，故不可观测；一旦下批接入真实端点即暴露。
- 改法：`BridgeProviderEvent` 增 `from`/request 关联字段或 Hub 侧按 request 聚合 Event 随 Response 回送；收 Response 后再 drain 一轮再返回。

### Nit

**N1 — `event.*` 前缀过宽，可能捕获枚举外 topic 后被下游静默丢弃**

- 位置：`provider.rs:62`（`event.*`）、`bridge_api.rs:106-126`（`serde_json::from_value::<BridgeEvent>`）、`protocol.rs:70-134`（`BridgeEventMethod` 为封闭枚举，无 `#[serde(other)]`）。
- `event.*` 匹配所有 `event.` 前缀 topic；若端点 publish 了枚举外的 topic（如自定义 `event.foo`），会经 Hub 投递到 client，再在 `filter_map` 的 `Err` 分支被丢弃（仅 Warn）。`SUBSCRIBES` 常量里的 `event.agent_*`（`adaptors/rust/endpoint.rs:44`）同样落在 `event.*` 覆盖内。当前枚举已覆盖标准 topic，影响有限。
- 改法：订阅收敛到实际需要的 topic 集合，或给 `BridgeEventMethod` 加 fallback 变体，避免「订阅到了却丢弃」。

**N2 — 回归测试用 `emitter` 手动 publish，绕过 `register_language`/真实端点装配**

- 位置：`provider.rs:217-221`（直接 `attach("emitter")` + `announce_str(&[], &[])` + `publish`）。
- 测试对齐修复点（订阅机制）是合理的，但没有覆盖「真实注册端点 → publish → call_sync」的组合路径（与 S1 呼应）。
- 改法：与 S1 的端到端测试合并或互补。

**N3 — `host.pump_until_idle(50)` 固定轮数在 `new()` 中足够，但无注释说明为何 50 轮**

- 位置：`provider.rs:63`。当前仅 1 个 Subscribe 帧，50 轮绰绰有余；纯可读性，无需改动。

## 五、结论

- **B1 关闭：是。** 订阅侧根因已修，Hub 前缀匹配与广播投递链路可证，回归测试能证伪，事件收集分支不再是死代码。
- **Blocker 数量：0。** 本轮改动未引入新 Blocker。
- 可进入第 2 批；但建议在第 2 批移除回落前，优先处理 S2（timeout 失效/`spawn_blocking`）与 S4（事件相关性/迟到事件），并补 S1 的端到端事件测试——否则单轨化后，事件丢失与超时不可诊断会被放大，且事件承载机制缺少回归保护。S3（源侧 publish）为下批既定范围，按计划接入即可。
