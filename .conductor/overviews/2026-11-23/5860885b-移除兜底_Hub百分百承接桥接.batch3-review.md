## 1. 核查点 1 — 事件流 publish

### 1.1 publish 帧 → event 帧 → host 订阅链路：**成立**

完整链路逐环验证：

1. `hub-stdio.ts:112` `publishSink = (event) => runtime.publish(event.method, ...)` → **topic = event.method**（如 `event.progress`）。
2. `runtime.ts:39` `publish(topic, payload)` → `publishFrame(topic, ...)` → Hub `route_frame → broadcast`（`hub.rs:332`）。
3. `broadcast` 对每个订阅者发 `BusFrame::Event { topic, payload, from }`，topic 原样保留（`hub.rs:350-355`）。
4. host 端点在 `provider.rs:108` `client.subscribe("event.*")`。`topic_matches("event.*", "event.progress")`：`capability_matches` 用 `strip_suffix('*')` 取前缀 `event.`，`"event.progress".starts_with("event.")` = true → **能收到**。
5. `call_sync` 的 `BusFrame::Event { topic, payload }` 分支收集为 `BridgeProviderEvent::new(topic, payload)`（`provider.rs:204-206`）；`bridge_api.rs:109-126` 转成 `BridgeEvent` 复用渲染链。

**结论：method 即 topic，host 能收到，链路闭合。** 新增测试 `real_node_events_reach_host_exchange` 与 `hub-stdio.test.ts` 分别覆盖全程与首段，非恒真断言。

### 1.2 双来源重复发布：**有潜在路径，当前被插件约定规避**

`hub-stdio.ts:79-86` 先 publish `context.emit` 的实时事件，再 publish `exchange.events`。是否重复取决于插件是否「既 emit 又把它塞进返回值」：

- compiler 适配器 `spawn.ts:44/157/247/309` 用 `events: emit ? [] : events`，`compiler.ts:129`、stopCompiler 同款 —— **emit 存在时清空返回 events**，规避重复。
- commitizen/commitlint/config 等插件只返回 `events`、不调 emit —— 走第二条，单次发布。
- agent 插件全程 emit、返回 `events: []`（`session.ts:296/378`）—— 走第一条，单次发布。

**当前无重复**，但这是「插件约定」而非框架硬保证：框架层无任何去重（无 event id、无 seen 集合）。任一插件若同时 emit 且返回同一事件，即双份渲染。与 1:1 路径 `stdio.ts:97-111` 的设计完全同构（那里也是双来源、同样靠约定），因此不算本批新引入的回归。**定级：Nit（契约脆弱，建议文档固化 `emit` 与返回 `events` 互斥）。**

### 1.3 被测试盲区掩盖的顺序性风险：**Should**

- 1:1 路径 emit 回调是 `async`，`writeEnvelope` 被 `await`（`stdio.ts:98`）；Hub 路径 emit 回调是 `async` 但内部 `publish(event)` **不 await**（`hub-stdio.ts:79-81`），`runtime.publish → write` 是同步 `void writeEnvelope`（`hub-stdio.ts:33-35`、`runtime.ts:39/51`）。
- 依赖「单一 writeChain 串行 + 按调用先后入链」保证 events 先于 response（envelope.ts:31-48）。`makeHubHooks` 里 publish 在 `return` 前同步调用，入链顺序正确。**正常路径安全**。
- 但 `runtime.publish` 是 fire-and-forget：`onRequest` 返回后 `serveRequest` 立即写 response（`runtime.ts:71`），两者共用 writeChain，顺序靠入链时刻。若未来 emit 改成异步（`await emit`）或插件在 emit 中 await 长操作，事件入链可能晚于 response，违反「events 先于 response」契约。测试仅断言「方法名集合」，**未断言顺序**，无法证伪此风险。**定级：Should（加一条 events-before-response 顺序断言）。**

## 2. 核查点 2 — hostRPC 往返

### 2.1 死锁判断：**不会死锁**（正常路径）

逐层拆解：

- `hostCall`（host-rpc.ts:106-136）：先建 pending[id]（`host-req-<hex>-<seq>`），再 `await transport.write(...)`，最后 `return await promise`。
- Hub 的 transport.write（hub-stdio.ts:118-133）：`await runtime.request(method, params)`，回来后 `handleHostResponse({id, result})`。
- `runtime.request`（runtime.ts:43-49）用 **correlationId = `endpointId-counter`**（如 `node-hub-1`），写入自己的 `this.pending` Map。
- `hostCall` 的 pending 表在 **globalThis 单例** `hostRpcState().pending`（host-rpc.ts:44-69），键是 `host-req-xxx`。

**两张表物理隔离、id 命名域不同、response 分别 resolve 各自的 pending**：

- Hub response 帧按 frame.id = correlationId 命中 `runtime.pending`（runtime.ts:58-63）→ resolve `runtime.request` → transport.write 继续 → `handleHostResponse` 按 `host-req` id 命中 hostCall 的 pending → resolve hostCall。**无冲突、无死锁。**

### 2.2 Blocker B1：`transport.write` 阻塞 + `runtime.request` 无超时 → hostCall 可永久挂起

反例构造（红队核心发现）：

1. `hostCall` 的 30s 超时挂在 `new Promise` 内部（`host-rpc.ts:120-128`），但真正消费它的是函数末尾的 `return await promise`（:135）。
2. 在 Hub 路径，函数卡在**更早的** `await transport.write(...)`（:130）；而该 write 的 `await runtime.request(...)`（hub-stdio.ts:121）在 response 丢失时**永不 resolve**——`runtime.request` 没有超时（runtime.ts:43-49 只 set + write），`runtime.handle` 对未知/丢失 frame 直接 return（:55/60）。
3. 后果链：response 因任一原因不到（handler panic、`send_to` 失败 detach `host-rpc` 端点、Node stdin 帧损坏被 `decodeFrame` catch 吞掉 `runtime.ts:55`）→ `runtime.request` 永久 pending → `transport.write` 永久 pending → hostCall **执行不到 `return await promise`** → 30s 超时虽 reject 了那个 promise，但**无人 await 它** → Node 抛出 unhandled rejection，且 tool 调用协程永久悬挂。

对比 1:1：transport.write 是 `await writeEnvelope(envelope)`（stdio.ts:42-44），总是立即 resolve，`return await promise` 必达，超时有效。**本批把 hostCall 的 transport 从「无阻塞写」换成「阻塞等响应写」，恰恰踩在超时机制的时序前提上。**

- 触发概率低（依赖异常路径），但性质是「永久挂起 + unhandled rejection」，且涉及 agent 全部工具调用（`agent.tool.exec` → hostCall，tools.ts:42）与全部 fs 操作（`fs.ts` 多处）。
- **定级：Blocker。** 修复方向：给 `runtime.request` 加超时并在 catch 里 reject，或把 hostCall 的 `return await promise` 与 `transport.write` 并行（`const p = promise; void transport.write(...).catch(reject); return await p`），别让内层写阻塞超时消费。

### 2.3 附带观察：错误 code 语义漂移（Nit）

`HostRpcHandlerBridge` 把 handler 的 Err 统一包成 `E_INTERNAL`（provider.rs:60-63），而 1:1 路径用 `E_HOST_RPC`（process.rs:311）。Node 端 catch 只做 `detail.code ?? 'E_INTERNAL'`（hub-stdio.ts:128），错误码对上层不可辨。低严重度。

## 3. 核查点 3 — 通配路由

### 3.1 `host.*` 不误捕获 `hostname.foo`：成立

`capability_matches`（hub.rs:442-447）：`pattern.strip_suffix('*')` → `"host."`；`"hostname.foo".starts_with("host.")` = false（`hostname` 第 6 字符是 `e` 非 `.`）。测试 `wildcard_only_matches_prefix` 覆盖前缀语义。**无误捕获。**

### 3.2 精确优先生效：成立

`route_request`（hub.rs:360-381）先取 `capability_index.get(&capability)` 精确列表；非空直接用，空才回退通配。测试 `wildcard_capability_routes_host_rpc` 验证通配命中，但**未验证「精确存在时不走通配」**——建议补一条反证测试（同时声明 `host.fs.read` 精确与 `host.*`，断言路由到精确端点）。**Nit。**

### 3.3 `topic_matches` 与 `capability_matches` 同语义：无隐患

`topic_matches` 现直接委托 `capability_matches`（hub.rs:436-438），二者原本都是「尾部 `*` 前缀匹配」（原 `wildcard_only_matches_prefix` 断言一致）。合并是去重而非语义变更。注意：`*` 仅支持**结尾**（`strip_suffix`），中间通配不支持——当前无此用法，**Nit**。

### 3.4 通配回退的一个聚合行为（Nit）

hub.rs:373-378 把所有匹配的通配 pattern 的 provider **全部 flat_map 收集**，再交给 `policy.select` 轮询。当前只有 `host.*` 一个通配端点，无影响；若将来出现多个重叠通配前缀（如 `host.*` 与 `host.fs.*`），同一 capability 会拿到合并 provider 列表。可接受，但需知晓。

## 5. 核查点 5 — host handler 事件丢失

### 5.1 确认丢弃

`HostRpcHandlerBridge::on_request`（provider.rs:52-65）：

```rust
Ok((result, _events)) => Ok(result),
```

`HostRpcHandler::handle` 返回 `(Value, Vec<BridgeEvent>)`（lib.rs:26-32），`_events` 被显式丢弃。而 BusFrame 的 `Response` 只有 `{id, result, error}`（无 events 字段），**即使想传也无帧格式承载**。

对比 1:1 路径：`handle_host_request` 把 events 塞进 `HostResponse.events`（process.rs:302-307），Node 端 `handleHostResponse` 解析进 `HostExchange.events`（host-rpc.ts:100-103）。语义确实不对称。

### 5.2 严重度评估：**Should，非 Blocker**

证据：

- 当前所有 `hostCall` 调用点（fs.ts 全部、`agent.tool.exec` tools.ts:42、schema-tools）**只读 `exchange.result`，无一处消费 `exchange.events`**。grep 全仓无 `hostCall(...).events` 消费。
- host_rpc 各 domain（exec/git/fs/pm/progress/interaction）几乎不产出非空 `BridgeEvent`（子模块中无 `BridgeEvent::` 构造，事件信息多序列化进 result JSON；测试 `host_rpc.rs:523` 断言 `events.is_empty()`）。

即当前「丢失」的是事实上的空集，无可见功能退化。**但这是契约缺口**：agent 工具未来若需经 host RPC 流式回传进度（如长 exec），Hub 路径会静默丢失。**定级：Should（登记为后续项，补帧字段或显式文档声明 host RPC 不产事件）。**

## 6. 核查点 6 — 删回落安全性

### 6.1 Blocker B2：长任务 active/shutdown 在 Hub 路径已断裂

这是删回落的最大障碍，且**当前命中 Hub 时就已退化**（被回落掩盖）：

**(a) provider 路径恒返回 `active: None`。** `bridge_api.rs:137-140` 构造 `BridgeDispatchResult { exchange, active: None }`。而 1:1 路径 `collect_bridge_exchange`（requests.rs:157-172）在 `is_long_running_request` 为真时 `Some(call)` 带回活跃句柄。

**(b) 长任务运行期事件无人消费。** `compiler.dev` 立即返回 `longRunning: true`（compiler-shared.ts:209/219、spawn.ts:244），响应后由 worker 持续 emit 运行期日志。`maybe_wait_for_shutdown`（long_running.rs:38-63）在 `active: None` 时走 `else { cancellation.cancelled().await }`——**只等 Ctrl-C，不 `next_event()`**。这些事件虽被 publish 到 Hub，但 `call_sync` 已返回，无人 pump 到 host 端点，运行期进度/日志丢失。`compiler.dev` 默认全量切片加载（slices.ts:65-68），必然命中此路径。

**(c) shutdown 请求走错通道。** `long_running.rs:81` 的 `dispatch_bridge_request(&self.node_bridge.compiler_stop_request())` 用的是 **1:1 `node_bridge` 客户端**，不是 Hub provider。Hub 模式下 `call_bridge` 走 provider，不会触发 node_bridge 的 1:1 子进程 `open_call`；此处才首次 spawn 一个**全新的** 1:1 进程，其 compiler 插件 `activeCompiler = null`，`compiler.stop` 停不掉 hub `node-hub` 进程里真正运行的 dev server。**删掉 1:1 回落后 `dispatch_bridge_request` 这条 shutdown 路径直接失效。**

**定级：Blocker。** 删回落前必须先让 provider 路径能带回 `BridgeActiveCall` 等价物（或改由 Hub 端点承载长任务生命周期与 stop）。

### 6.2 bridge.\* 内建方法无 Hub provider — 删即断

`endpointCapabilities()`（hub-stdio.ts:45-56）只 announce 插件 methods，**刻意排除了 `BRIDGE_METHODS`**（注释 :53-54 称"由宿主提供"）。但宿主侧只 attach 了两类端点：`host-rpc`（`host.*`）与 register_language 的 echo（`echo.ping/echo.upper`，endpoint.rs:43）。**没有任何端点声明 `bridge.ping/bridge.shutdown/bridge.metrics/bridge.heartbeat/plugins.resolve`。**

经 Hub 请求这些方法 → 精确未命中 + `host.*` 通配不匹配 `bridge.*` → `E_METHOD_NOT_FOUND` → 当前靠回落 1:1（`node_bridge`）兜住。`core.rs:110-112` 的 `handshake_preview`、`requests.rs` 的 `shutdown_request/metrics_request/subscribe_request`、`bridge_api.rs:359` 的 `toolchain.describe` 等仍依赖 node_bridge。**删回落这些全断。** **定级：Blocker（删回落的硬前置）。**

### 6.3 LANIA_BRIDGE_MODE 残留 — 回落载体仍在

- `stdio.ts:29-32` 的 `LANIA_BRIDGE_MODE === 'hub'` 分支 + 其后的整段 1:1 逻辑仍是回落的物理载体；`hub_mode_command` 正是靠注入该变量切换。
- 解读：删回落后不能简单删掉整个 1:1 stdio 路径——`node_bridge`（1:1 客户端）仍被 `call_runtime_bridge`、`toolchain_command`、shutdown、handshake 使用（§6.2）。"删 call_bridge 回落"≠"删 node_bridge"。这是一处易踩的认知陷阱，须在删除清单里逐项标注归属。**定级：Should（删前出一份精确删除边界清单）。**

### 6.4 超时双计时叠加（Should）

`call_bridge` 外层 `tokio::time::timeout(policy.timeout_ms, provider.call())`（bridge_api.rs:97-101），provider 内层 `call_sync` 又有 `CALL_TIMEOUT = 30s`（provider.rs:44/180）。若 `policy.timeout_ms` 配成 <30s，外层先触发 → 回落；配 >30s 内层先 E_TIMEOUT → 回落。两套超时语义未对齐，删回落后外层的任何超时都直接变成 `E_TIMEOUT` 失败。建议统一到策略值。

## 8. 最终裁决
